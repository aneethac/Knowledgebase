Principal Answer Memory Pattern

Problem → Scale → Constraints → Decision → Why → Trade-off → Failure Handling → Operations → Result

Use: “The requirement was X, at Y scale, with Z constraint. I chose A because B. The trade-off was C, mitigated by D. We measured E and achieved F.”

End-to-End Delivery Memory Pattern

Discover → Requirements/NFRs → HLD → LLD → Build → Test → Deploy → Validate → Operate → Optimize

Discovery should cover business outcome, sources, consumers, grain, volume/growth, SLA, batch vs streaming, lateness, history/backfill, DQ thresholds, PII/security, retention, RPO/RTO, cost and acceptance criteria.

HLD covers system boundaries, major components, data flows, trust boundaries, platform decisions, integration patterns, recovery and ADRs. LLD covers schemas, keys, incremental predicates, orchestration, retry/replay, SCD rules, DQ and monitoring.

Load Pattern Decision

Pattern Best fit Risk Control
Full reload small/reference data repeated compute size/runtime threshold
Append immutable events duplicates deterministic key + dedupe
Watermark reliable timestamp/key late updates overlap window + dedupe
CDC mutable high-volume source ordering/deletes/replay sequence + idempotent merge
Snapshot diff no CDC available comparison cost hashes + scoped partitions

Idempotency, Replay and Backfill

Use deterministic keys, replayable landing, process IDs, deduplication, merge/upsert, persisted checkpoints, parameterized backfills, validation-before-publish and input/output audit metadata. In distributed systems, explain exactly-once business effects rather than casually promising exactly-once delivery.

Data Quality Contract

Landing: arrival, schema, size/count, checksum, freshness.
Structural: not-null, uniqueness, FK, accepted values.
Business: domain rules and reconciliation.
Temporal: SCD2 overlap and effective dates.
Distribution: volume/null/statistical drift.
Every critical rule needs threshold, severity, owner, action and escalation.

Observability / SRE

Monitor freshness, volume, quality, performance, cost, lineage and reliability.
Incident response: Detect → Contain → Recover → RCA → Prevent.

Snowflake Principal Deep Dive

Mental model: cloud services/control plane + independent virtual warehouse compute + centralized micro-partitioned storage.

Performance order: Query Profile → scan/pruning → filters/joins → recomputation → aggregates/materialization → concurrency → warehouse size → benchmark cost and latency.

Scale up for an individual heavy query; scale out/multi-cluster for concurrency/queueing.

Know conceptual roles of Streams, Tasks, Dynamic Tables and dbt.

1. System Architecture & 6-Tier Schema Topology

Overview

The BIW Cloud Data Warehouse is built on a decoupled 6-tier schema topology on Snowflake. This architecture isolates each data processing concern so that upstream schema changes never cascade to downstream consumers.

Azure Data Lake (EDL)
        │
        ▼
   STG (Staging)          ← Transient landing from COPY INTO
        │
        ▼
   PSG (Persisted Staging) ← Raw CDC history retained
        │
        ▼
   WRK / CR (Work Layer)  ← Deduplication, window functions, surrogate keys
        │
        ▼
   BIW_DWH / DM (Core)   ← Kimball Star Schema (dim_*, fct_*)
        │
        ▼
   OUT / Views (Consumer) ← Logical views for BI tools and Feature Stores

Layer Definitions

Layer Schema Materialization Storage Type Purpose
EDL External Stage Stage Azure ADLS Raw file landing (CSV, Parquet, Delta)
STG STG Transient Table TRANSIENT Fast COPY INTO from stage, truncated after load
PSG PSG Permanent Table PERMANENT Persisted raw CDC history with audit columns
WRK WRK Transient Table TRANSIENT Intermediate deduplication and key resolution
CR CR Permanent Table PERMANENT Common reference data, lookup tables
DM / BIW_DWH BIW_DWH Permanent Table PERMANENT Conformed Kimball Star Schema dimensions & facts
OUT OUT View N/A Consumer abstraction views for BI and ML

3. Data Ingestion & Incremental Load Patterns

Pattern 1 — Initial Historical Bulk Load

-- Step 1: Create file format
CREATE OR REPLACE FILE FORMAT BIW_PARQUET_FORMAT
    TYPE = 'PARQUET'
    SNAPPY_COMPRESSION = TRUE;

-- Step 2: Bulk COPY INTO staging
COPY INTO STG.RMS_PROD_ITEM_STG
FROM @BIW_AZURE_STAGE/rms/prod_item/
FILE_FORMAT = (FORMAT_NAME = 'BIW_PARQUET_FORMAT')
ON_ERROR = 'CONTINUE'
PURGE = FALSE;

Pattern 2 — CDC Incremental Merge

-- Step 1: Land delta records into STG
COPY INTO STG.RMS_PROD_ITEM_STG
FROM @BIW_AZURE_STAGE/rms/prod_item/delta/
FILE_FORMAT = (FORMAT_NAME = 'BIW_PARQUET_FORMAT')
ON_ERROR = 'CONTINUE';

-- Step 2: Merge CDC into PSG (persistent raw history)
MERGE INTO PSG.RMS_PROD_ITEM_TXN AS TGT
USING STG.RMS_PROD_ITEM_STG AS SRC
ON TGT.ITEM_IDNT = SRC.ITEM_IDNT
   AND TGT.CDW_PROCESS_KEY = SRC.CDW_PROCESS_KEY
WHEN NOT MATCHED THEN INSERT (
    ITEM_IDNT, ITEM_DESC, CATEGORY_CDE, UNIT_RETAIL_AMT,
    CDW_RECD_LOAD_DT, CDW_PROCESS_KEY, CDW_SOURCE_SYSTEM_CDE
) VALUES (
    SRC.ITEM_IDNT, SRC.ITEM_DESC, SRC.CATEGORY_CDE, SRC.UNIT_RETAIL_AMT,
    CURRENT_TIMESTAMP(), SRC.CDW_PROCESS_KEY, 'RMS'
);

4. Kimball Dimensional Modeling Standards

Star Schema Design Rules

  1. Fact Tables — store measurable, numeric events at atomic grain
  2. Dimension Tables — store descriptive context for fact analysis
  3. Conformed Dimensions — shared across multiple subject area facts
  4. Surrogate Keys — all dimension joins via system-generated hash keys
  5. Atomic Grain — Product-Item × Location × Day (PLU-ATM level)

Fact Table Standards

-- Atomic Fact Table Example
CREATE OR REPLACE TABLE BIW_DWH.FCT_SALES_TRANSACTION_PLU_ATM (
    SALES_TRAN_KEY          NUMBER NOT NULL,        -- Surrogate Key
    TRAN_DT                 DATE NOT NULL,          -- Degenerate Dimension
    PROD_ITEM_KEY           NUMBER NOT NULL,        -- FK → DIM_PROD_ITEM
    ORG_LOC_KEY             NUMBER NOT NULL,        -- FK → DIM_ORG_LOC
    SALES_QTY               NUMBER(15,3),           -- Additive Fact
    RETAIL_AMT              NUMBER(15,2),           -- Additive Fact
    DISCOUNT_AMT            NUMBER(15,2),           -- Additive Fact
    CDW_RECD_LOAD_DT        TIMESTAMP_NTZ,
    CDW_PROCESS_KEY         NUMBER
)
CLUSTER BY (TRAN_DT, ORG_LOC_KEY);

Dimension Table Standards

-- Conformed Dimension Example (SCD Type 2)
CREATE OR REPLACE TABLE BIW_DWH.DIM_PROD_ITEM (
    PROD_ITEM_KEY           NUMBER NOT NULL,        -- Surrogate Key (PK)

    ITEM_DESC               VARCHAR(200),
    CATEGORY_CDE            VARCHAR(10),
    CATEGORY_DESC           VARCHAR(100),

    IS_MERCH_RANGED_FLG     CHAR(1),

    CDW_RECD_LOAD_DT        TIMESTAMP_NTZ,
    CDW_RECD_CLOSE_DT       TIMESTAMP_NTZ,
    CDW_RECD_CURR_FLG       CHAR(1) DEFAULT 'Y',
    CDW_PROCESS_KEY         NUMBER
);

5. Slowly Changing Dimensions (SCD) Implementation

SCD Type 1 — Overwrite (No History)

Used for: Corrections, typos, non-analytically significant attribute changes.

MERGE INTO BIW_DWH.DIM_PROD_ITEM AS TGT
USING WRK.PROD_ITEM_WRK AS SRC
ON TGT.ITEM_IDNT = SRC.ITEM_IDNT
   AND TGT.CDW_RECD_CURR_FLG = 'Y'
WHEN MATCHED AND (
    TGT.ITEM_DESC <> SRC.ITEM_DESC OR
    TGT.CATEGORY_CDE <> SRC.CATEGORY_CDE
) THEN UPDATE SET
    TGT.ITEM_DESC       = SRC.ITEM_DESC,
    TGT.CATEGORY_CDE    = SRC.CATEGORY_CDE,
    TGT.CDW_RECD_LAST_UPD_DT = CURRENT_TIMESTAMP();

SCD Type 2 — History Tracking (Full Versioning)

Used for: Analytically significant attribute changes (price, category reclassification, range status).

-- Step 1: Expire active row
UPDATE BIW_DWH.DIM_PROD_ITEM
SET CDW_RECD_CURR_FLG  = 'N',
    CDW_RECD_CLOSE_DT  = CURRENT_TIMESTAMP(),
    CDW_RECD_LAST_UPD_DT = CURRENT_TIMESTAMP()
WHERE ITEM_IDNT IN (
    SELECT SRC.ITEM_IDNT
    FROM WRK.PROD_ITEM_WRK SRC
    JOIN BIW_DWH.DIM_PROD_ITEM TGT
        ON SRC.ITEM_IDNT = TGT.ITEM_IDNT
        AND TGT.CDW_RECD_CURR_FLG = 'Y'
    WHERE SRC.CATEGORY_CDE <> TGT.CATEGORY_CDE
       OR SRC.UNIT_RETAIL_AMT <> TGT.UNIT_RETAIL_AMT
)
AND CDW_RECD_CURR_FLG = 'Y';

-- Step 2: Insert new active row
INSERT INTO BIW_DWH.DIM_PROD_ITEM (
    PROD_ITEM_KEY, ITEM_IDNT, ITEM_DESC, CATEGORY_CDE,
    UNIT_RETAIL_AMT, CDW_RECD_LOAD_DT, CDW_RECD_CLOSE_DT,
    CDW_RECD_CURR_FLG, CDW_PROCESS_KEY
)
SELECT
    {{ dbt_utils.generate_surrogate_key(['ITEM_IDNT', 'CURRENT_TIMESTAMP()']) }},
    SRC.ITEM_IDNT, SRC.ITEM_DESC, SRC.CATEGORY_CDE,
    SRC.UNIT_RETAIL_AMT, CURRENT_TIMESTAMP(), '9999-12-31'::TIMESTAMP_NTZ,
    'Y', SRC.CDW_PROCESS_KEY
FROM WRK.PROD_ITEM_WRK SRC
WHERE SRC.ITEM_IDNT IN (
    SELECT ITEM_IDNT FROM BIW_DWH.DIM_PROD_ITEM
    WHERE CDW_RECD_CURR_FLG = 'N'
    AND CDW_RECD_CLOSE_DT >= CURRENT_TIMESTAMP() - INTERVAL '1 minute'
);

UPDATE BIW_DWH.DIM_ITEM_SCD2 target
SET 
    CDW_RECD_CLOSE_DT = src.EFFECTIVE_TS,
    CDW_RECD_CURR_FLG = 'N',
    CDW_RECD_LAST_UPD_DT = CURRENT_TIMESTAMP()
FROM WRK.WRK_ITEM_CHANGES src
WHERE target.ITEM_IDNT = src.ITEM_IDNT 
  AND target.CDW_RECD_CURR_FLG = 'Y'
  AND target.CDW_HASH_KEY <> src.CDW_HASH_KEY;

from pyspark.sql.window import Window

fs = FeatureStoreClient()

# Step 1: Load Silver Delta table with time travel for PIT integrity
silver_df = spark.read.format("delta") \
    .option("timestampAsOf", training_cutoff_date) \
    .load("/mnt/silver/product_range")

# Step 2: Compute rolling features
window_4wk = Window.partitionBy("ITEM_KEY", "LOC_KEY") \
    .orderBy("EVENT_DATE") \
    .rowsBetween(-28, -1)

features_df = silver_df \
    .withColumn("SALES_ROLL_4WK_AVG",
        F.avg("SALES_QTY_AMT").over(window_4wk)) \
    .withColumn("PROMO_WEEKS_ROLL_4WK",
        F.sum("IS_ON_PROMO_FLG").over(window_4wk)) \

        F.when(F.col("CURR_PRICE_AMT") != F.lag("CURR_PRICE_AMT", 1)

        .orderBy("EVENT_DATE")), 1).otherwise(0))

    name       = "pfs.item_loc_daily_features",
    df         = features_df,

10. Deep-Dive Technical Q&A

Q1: How do you handle late-arriving dimension records?

“When a sales transaction arrives before its corresponding Product master record has landed in our dimension table, a standard inner join would drop the revenue record, and a left join leaves a NULL foreign key breaking drill-down reporting.

I implement the Inferred Dimension Member Pattern. When the fact model encounters an unknown NATURAL_KEY, it dynamically inserts a placeholder row into the dimension table with a generated surrogate key, sets descriptive attributes to Inferred / Unmapped, and flags IS_INFERRED_FLG = 'Y'.

When the actual dimension record eventually arrives in a later batch, our dbt SCD Type 1 update logic overwrites the inferred placeholder attributes with true master data while preserving the original surrogate key connection.”

Q2: Why Kimball Dimensional Modeling over Data Vault 2.0?

“We evaluated both methodologies during our high-level architecture phase. Data Vault 2.0 offers superior agility for multi-source integration with frequent schema changes, but it introduces significant join complexity — Hubs, Links, Satellites — that slows down ad-hoc SQL querying and BI tools.

Because our primary operational consumers were PowerBI dashboards, business analysts, and downstream feature extractors requiring fast aggregated queries, Kimball Dimensional Modeling was the optimal choice. It provided conformed, business-intuitive Star Schemas that delivered superior query performance on Snowflake while making it seamless for business teams to self-serve.”

Q3: How do you prevent data pipeline failures from impacting downstream ML models?

“We implement three protection layers:

1. Idempotent Pipeline Design: Every dbt incremental model uses unique_key with merge strategy — re-running the same pipeline twice produces identical results with no duplicate records.*

2. Data Quality Gates: dbt test assertions run as blocking gates between pipeline stages. If row counts drop by more than 5% compared to the previous run, or if referential integrity checks fail, the downstream stages are blocked and on-call engineers are alerted.*

3. Feature Store Versioning: In Databricks, we never overwrite feature tables in place. We write to a new Delta version and only promote to the CURRENT feature version pointer after automated validation passes. ML models continue reading the previous validated version until promotion succeeds.”*

Q4: How do you manage schema evolution without breaking consumers?

“Schema evolution is one of the trickiest operational challenges in data engineering. Our strategy has three components:

1. Consumer View Abstraction: All downstream consumers connect via logical Snowflake views in the OUT layer — never directly to physical tables. When a source adds a column or renames a field, we update only the physical model and adjust the view projection without touching consumer queries.*

2. dbt on_schema_change = append_new_columns: For incremental models, we configure dbt to automatically append new columns from source without failing the pipeline.*

3. Delta Lake Schema Evolution: In Databricks, Delta Lake’s mergeSchema = true option allows new source columns to be safely added to existing Delta tables during merge operations, without requiring table recreation.”*
