5. Deletion Vectors

AspectDetail
WhatA bitmap that marks rows as "deleted" within a Parquet file without rewriting the file
WhyDELETE/UPDATE/MERGE no longer need to rewrite entire files — just append a deletion vector
Performance2-10x faster DELETE/UPDATE/MERGE on large tables
EnableALTER TABLE t SET TBLPROPERTIES ('delta.enableDeletionVectors' = true)
DefaultEnabled by default on new tables (DBR 14.0+)
Read impactReaders apply the deletion vector as a filter — slight overhead, but much less than rewriting
Exam tipDeletion vectors make MERGE cheaper because only the deletion bitmap is written, not new Parquet files

4. Common Exam Traps

TrapCorrect Answer
"VACUUM deletes the transaction log"NO — VACUUM only deletes unreferenced DATA files. The log is separate.
"OPTIMIZE deletes old files"NO — OPTIMIZE creates new compacted files. Old files remain until VACUUM.
"Shallow clone copies data"NO — Shallow clone only copies metadata. Data files are referenced, not duplicated.
"DROP external table deletes data"NO — DROP external table removes metadata only. Data files remain at the LOCATION.
"Streaming tables support UPDATE/DELETE"NO — Streaming tables are append-only. Use materialized views for full DML.
"VACUUM with 0 hours is safe"NO — VACUUM RETAIN 0 HOURS breaks concurrent readers. Minimum safe retention = 7 days (168 hours).
"Auto Loader is a SQL command"NO — Auto Loader uses spark.readStream.format('cloudFiles'). COPY INTO is the SQL alternative.
"Materialized Views store a query, not data"NO — MVs store pre-computed data (unlike standard views). They are refreshed, not re-executed.
"Time Travel works forever"NO — Limited by VACUUM retention (default 7 days for data files). After VACUUM, old versions are gone.
"All clusters have Photon"NO — Photon is on SQL Warehouses (always) and Photon-enabled clusters (opt-in).

## Delta Lake — Complete Feature Reference

---

### 1. What Makes Delta Lake Different from Plain Parquet

| Feature | Parquet | Delta Lake |
| --- | --- | --- |
| ACID Transactions | No | Yes — via `_delta_log/` |
| Time Travel | No | Yes — `VERSION AS OF`, `TIMESTAMP AS OF` |
| Schema Enforcement | No (schema-on-read) | Yes — rejects bad writes |
| Schema Evolution | Manual | `ALTER TABLE ADD COLUMNS` or `mergeSchema` option |
| UPDATE/DELETE/MERGE | No | Yes — full DML support |
| Data Skipping | No | Yes — min/max stats per file per column |
| Streaming Source/Sink | Limited | Yes — exactly-once with checkpointing |
| Audit History | No | Yes — `DESCRIBE HISTORY` |

### 2. Delta Transaction Log (`_delta_log/`)

| Concept | Detail | Exam Tip |
| --- | --- | --- |
| **Location** | `_delta_log/` directory inside table directory | Every table has one |
| **Format** | JSON files (one per commit) + Parquet checkpoints every 10 commits | Checkpoint = snapshot for fast reads |
| **What it records** | Add file, remove file, metadata changes, protocol changes | Each commit is atomic |
| **Optimistic concurrency** | Writers check if conflicts exist at commit time | `ConcurrentAppendException` if conflict |
| **Conflict resolution** | File-level (not row-level) — two writers to different files = no conflict | This is why partitioning helps concurrency |

### 3. Time Travel

| Method | Syntax | Use Case |
| --- | --- | --- |
| **By version** | `SELECT * FROM table VERSION AS OF 42` | Audit, debug, reproduce |
| **By timestamp** | `SELECT * FROM table TIMESTAMP AS OF '2026-08-01'` | Point-in-time reporting |
| **Restore** | `RESTORE TABLE table TO VERSION AS OF 42` | Undo bad writes |
| **History** | `DESCRIBE HISTORY table` | See all commits with timestamps, operations, users |
| **Retention** | Default 30 days for data files | Controlled by `delta.logRetentionDuration` (log) and `delta.deletedFileRetentionDuration` (data) |

### 4. Table Maintenance Commands

| Command | What It Does | When to Run | Exam Tip |
| --- | --- | --- | --- |
| **OPTIMIZE** | Compacts small files into larger ones (\~1 GB target) | After many small writes (streaming, frequent appends) | Does NOT delete old files — just adds new compacted ones |
| **OPTIMIZE ... ZORDER BY** | Compacts + co-locates data by specified columns | When queries filter on specific non-partition columns | Max 4 columns recommended; diminishing returns after |
| **VACUUM** | Deletes files older than retention period that are no longer referenced | Weekly or after OPTIMIZE | Default retention = 7 days. **Cannot undo VACUUM** — breaks time travel for vacuumed versions |
| **ANALYZE TABLE** | Computes column-level statistics for the optimizer | After large data changes; before expensive queries | Critical for correct join strategy selection |
| **DESCRIBE DETAIL** | Shows file count, size, partition columns, table properties | Diagnostic — check table health | Key fields: `numFiles`, `sizeInBytes`, `partitionColumns` |
| **DESCRIBE HISTORY** | Shows commit log with timestamps, operations, metrics | Debugging, auditing | Shows `operationMetrics` (rows written, files added) |

### 5. Deletion Vectors

| Aspect | Detail |
| --- | --- |
| **What** | A bitmap that marks rows as "deleted" within a Parquet file without rewriting the file |
| **Why** | DELETE/UPDATE/MERGE no longer need to rewrite entire files — just append a deletion vector |
| **Performance** | 2-10x faster DELETE/UPDATE/MERGE on large tables |
| **Enable** | `ALTER TABLE t SET TBLPROPERTIES ('delta.enableDeletionVectors' = true)` |
| **Default** | Enabled by default on new tables (DBR 14.0+) |
| **Read impact** | Readers apply the deletion vector as a filter — slight overhead, but much less than rewriting |
| **Exam tip** | Deletion vectors make MERGE cheaper because only the deletion bitmap is written, not new Parquet files |

### 6. Change Data Feed (CDF)

| Aspect | Detail |
| --- | --- |
| **What** | Records row-level changes (insert, update_preimage, update_postimage, delete) for downstream consumers |
| **Enable** | `ALTER TABLE t SET TBLPROPERTIES ('delta.enableChangeDataFeed' = true)` |
| **Query** | `SELECT * FROM table_changes('my_table', 2)` — changes since version 2 |
| **Use case** | Incremental ETL: downstream tables read only changed rows instead of full table |
| **Storage** | Changes stored in `_change_data/` directory inside the table |
| **Exam tip** | CDF is the foundation for incremental MERGE patterns — enables "process only what changed" |

### 7. Liquid Clustering vs Partitioning vs Z-Order

| Aspect | PARTITION BY | Z-ORDER BY | CLUSTER BY (Liquid) |
| --- | --- | --- | --- |
| **Set at** | CREATE TABLE time only | On-demand with OPTIMIZE | CREATE TABLE or ALTER TABLE anytime |
| **Change columns** | Cannot change — rebuild required | Can change anytime | Can change with ALTER TABLE |
| **How it works** | Physical directories per value | Interleaved sort within files | Hilbert-curve layout within files |
| **Best for** | Low-cardinality (date, region) | Ad-hoc optimization, 1-4 columns | Any cardinality, up to 4 columns |
| **Small file problem** | Yes — high cardinality = millions of tiny files | No | No |
| **Incremental** | N/A | Must re-run OPTIMIZE on all data | OPTIMIZE processes only new/changed files |
| **Exam tip** | Legacy — use Liquid Clustering for new tables | Being replaced by Liquid Clustering | **Recommended approach** for all new Delta tables |

## Data Engineering — ETL, Pipelines, Auto Loader & SDP

---

### 1. Auto Loader (cloudFiles)

| Aspect | Detail |
| --- | --- |
| **What** | Incrementally and efficiently processes new files as they arrive in cloud storage |
| **How** | Uses file notification (event-based) or directory listing to detect new files |
| **Format** | `spark.readStream.format('cloudFiles')` |
| **Key option** | `.option('cloudFiles.format', 'json')` — supports JSON, CSV, Parquet, Avro, ORC, text, binary |
| **Schema inference** | Automatic with `cloudFiles.inferColumnTypes = true` |
| **Schema evolution** | `cloudFiles.schemaEvolutionMode = addNewColumns` — auto-adds new columns |
| **Rescue column** | `_rescued_data` — captures data that doesn't match the schema instead of failing |
| **Checkpoint** | Tracks which files have been processed — exactly-once semantics |

**Two modes:**

| Mode | How | When to Use |
| --- | --- | --- |
| **Directory Listing** | Lists the directory periodically | < 10K files/day, simpler setup |
| **File Notification** | Cloud events (Azure Event Grid, AWS SNS/SQS) | > 10K files/day, lower latency |

**Exam-critical pattern:**
```python
df = (spark.readStream
  .format('cloudFiles')
  .option('cloudFiles.format', 'json')
  .option('cloudFiles.inferColumnTypes', 'true')
  .option('cloudFiles.schemaLocation', '/path/to/schema')
  .load('/path/to/source/')
)
df.writeStream.option('checkpointLocation', '/path/to/checkpoint').table('bronze.events')
```

### 2. Spark Declarative Pipelines (SDP, formerly DLT)

| Concept | Detail | Exam Tip |
| --- | --- | --- |
| **What** | Declarative ETL framework — you define WHAT, Spark handles HOW | You write `CREATE STREAMING TABLE` or `CREATE MATERIALIZED VIEW` |
| **Streaming Table** | Append-only table fed by a streaming source | Use for raw/bronze data, CDC |
| **Materialized View** | Auto-refreshed query result | Use for aggregations, gold layer |
| **Expectations** | Data quality constraints with actions | `CONSTRAINT valid_id EXPECT (id IS NOT NULL) ON VIOLATION DROP ROW` |
| **Pipeline modes** | Triggered (batch) or Continuous (streaming) | Triggered for cost savings; Continuous for low latency |
| **Development vs Production** | Dev mode = reuses cluster, fast iteration; Prod mode = new cluster per run | Always use Production for scheduled jobs |

**Expectations actions:**

| Action | Behavior | When to Use |
| --- | --- | --- |
| `ON VIOLATION WARN` | Logs the violation, keeps the row | Monitoring — see how many bad records |
| `ON VIOLATION DROP ROW` | Silently drops the row | Filter out bad data |
| `ON VIOLATION FAIL UPDATE` | Fails the entire pipeline | Critical data — no bad records allowed |

### 3. Structured Streaming Concepts

| Concept | Detail | Exam Tip |
| --- | --- | --- |
| **Trigger** | How often to process: `availableNow` (all pending, then stop), `processingTime` (interval), continuous | `availableNow` = batch-like but incremental |
| **Checkpoint** | Stores progress (which files/offsets processed) | Required for exactly-once; cannot change query between restarts without resetting |
| **Watermark** | Threshold for late data: `withWatermark('event_time', '10 minutes')` | Data arriving after watermark is dropped |
| **Output modes** | Append (new rows only), Complete (full result), Update (changed rows) | Append is most common; Complete for aggregations |

### 4. Medallion Architecture Exam Reference

| Layer | Purpose | Table Type | Data Quality | Consumers |
| --- | --- | --- | --- | --- |
| **Bronze** | Raw ingestion, append-only | Streaming Table | Minimal — schema enforcement only | Silver layer |
| **Silver** | Cleaned, conformed, deduplicated | Streaming Table or MV | High — expectations, null handling, type casting | Gold layer, data science |
| **Gold** | Business-ready aggregations | Materialized View | Highest — pre-aggregated, validated | Dashboards, reports, APIs |

### 5. COPY INTO vs Auto Loader

| Aspect | COPY INTO | Auto Loader |
| --- | --- | --- |
| **Type** | SQL command (batch) | Streaming source |
| **Idempotent** | Yes — tracks loaded files | Yes — via checkpoint |
| **Scale** | Millions of files (slower at very high volume) | Billions of files (file notification scales better) |
| **Schema evolution** | Manual | Automatic with rescue column |
| **Use case** | One-time loads, simple ETL | Production incremental ingestion |
| **Exam tip** | Good for ad-hoc; Auto Loader for production pipelines |

### 4. Common Exam Traps

| Trap | Correct Answer |
| --- | --- |
| "VACUUM deletes the transaction log" | NO — VACUUM only deletes unreferenced DATA files. The log is separate. |
| "OPTIMIZE deletes old files" | NO — OPTIMIZE creates new compacted files. Old files remain until VACUUM. |
| "Shallow clone copies data" | NO — Shallow clone only copies metadata. Data files are referenced, not duplicated. |
| "DROP external table deletes data" | NO — DROP external table removes metadata only. Data files remain at the LOCATION. |
| "Streaming tables support UPDATE/DELETE" | NO — Streaming tables are append-only. Use materialized views for full DML. |
| "VACUUM with 0 hours is safe" | NO — VACUUM RETAIN 0 HOURS breaks concurrent readers. Minimum safe retention = 7 days (168 hours). |
| "Auto Loader is a SQL command" | NO — Auto Loader uses `spark.readStream.format('cloudFiles')`. COPY INTO is the SQL alternative. |
| "Materialized Views store a query, not data" | NO — MVs store pre-computed data (unlike standard views). They are refreshed, not re-executed. |
| "Time Travel works forever" | NO — Limited by VACUUM retention (default 7 days for data files). After VACUUM, old versions are gone. |
| "All clusters have Photon" | NO — Photon is on SQL Warehouses (always) and Photon-enabled clusters (opt-in). |

## Spark Internals & Databricks Optimization — Complete Cheat Sheet

---

### 1. Query Lifecycle: What Happens When You Run a Query

| Step | What Happens | Key Detail |
| --- | --- | --- |
| **1. Parsing** | SQL text → Abstract Syntax Tree (AST) | Syntax errors caught here |
| **2. Analysis** | Resolves table/column names against Unity Catalog | "Table not found" errors here |
| **3. Logical Plan** | AST → logical operators (Scan, Filter, Join, Aggregate) | Describes WHAT to do, not HOW |
| **4. Catalyst Optimizer** | Rewrites logical plan (predicate pushdown, constant folding, join reorder) | This is Spark's "brain" — automatically makes your query smarter |
| **5. Physical Plan** | Chooses algorithms: which join type, scan method, shuffle strategy | You can see this with `EXPLAIN EXTENDED <query>` |
| **6. Code Generation (Photon/Tungsten)** | Compiles plan into executable bytecode | Photon (C++ engine on Databricks) replaces Tungsten for supported ops |
| **7. Execution** | Distributes tasks across executors in stages | Stages run in parallel where possible |
| **8. Write** | Results written to Delta files (Parquet + transaction log) | Commit recorded in `_delta_log/` |

---

### 2. How Work Maps: Query → Jobs → Stages → Tasks → Partitions

```
Query (1 SQL statement)
 └── Job (1 per action: INSERT, SELECT, etc.)
      └── Stage (separated by SHUFFLES — each shuffle = new stage)
           └── Tasks (1 task per data partition within that stage)
                └── Each task processes 1 partition of data on 1 CPU core
```

| Concept | What It Is | How Size Is Decided |
| --- | --- | --- |
| **Job** | One complete execution triggered by an action (write, collect, display) | 1 query = usually 1 job (can be more for subqueries) |
| **Stage** | A chunk of work that can run without a shuffle | Every shuffle (JOIN, GROUP BY, ORDER BY) creates a stage boundary |
| **Task** | The smallest unit of work — runs on 1 core, processes 1 partition | Number of tasks = number of partitions in that stage |
| **Partition** | A chunk of data (default \~128 MB target for reads) | Read partitions come from file layout; shuffle partitions from AQE |

---

### 3. Mapping to Compute Size (SQL Warehouse)

| Warehouse Size | Max Concurrent Tasks (approx) | Best For |
| --- | --- | --- |
| 2X-Small | 8 | Quick lookups, small tables |
| X-Small | 16 | Light dashboards |
| Small | 32 | Medium queries, dev/test |
| Medium | 64 | Production workloads |
| Large | 128 | Heavy ETL, large joins |
| X-Large+ | 256+ | Massive data processing |

> With 303 tasks on a Small warehouse (\~32 concurrent slots), tasks run in waves: \~32 at a time → 303/32 ≈ 10 waves. A bigger warehouse = more parallelism = fewer waves = faster.

### 4. What Triggers Each Operation

#### Scans (Reading Data)

| Trigger | What Happens | How to Optimize |
| --- | --- | --- |
| `FROM table` / any table reference | Reads Parquet files from cloud storage | Partition pruning, file pruning via stats |
| Full table scan (no filters) | Reads ALL files | Always add WHERE clauses on partition columns |
| Predicate pushdown | Filter pushed INTO the scan — reads less data | Spark does this automatically for supported predicates |
| Column pruning | Only reads columns you SELECT | Parquet is columnar — unused columns cost almost nothing |

#### Shuffles (Data Movement Across Network)

| Trigger | Why It Shuffles | Cost |
| --- | --- | --- |
| `JOIN` (most types) | Both sides must be co-located by join key | HIGH — serializes, writes to disk, sends over network, deserializes |
| `GROUP BY` / `DISTINCT` | All rows with same key must land on same partition | MEDIUM-HIGH |
| `ORDER BY` / `SORT BY` | Global ordering requires data movement | HIGH (global sort) |
| `WINDOW OVER (PARTITION BY ...)` | Rows in same partition-by group must be co-located | MEDIUM-HIGH |
| `UNION` / `MINUS` / `INTERSECT` | Deduplication requires co-location | MEDIUM |
| `INSERT INTO partitioned_table` | Data repartitioned by target partition column | MEDIUM |

#### Exchanges

| Type | When | Detail |
| --- | --- | --- |
| **HashExchange** | JOIN, GROUP BY | Hashes the key, sends to matching partition |
| **RangeExchange** | ORDER BY | Samples data, creates range boundaries |
| **BroadcastExchange** | Small table JOIN | Copies entire small table to every executor — NO shuffle on the big table |
| **SinglePartition** | Final aggregation | All data → 1 partition |

### 5. Join Strategies Spark Chooses (Automatically)

| Strategy | When Chosen | Performance |
| --- | --- | --- |
| **Broadcast Hash Join** | One side < 10 MB (default threshold) | FASTEST — no shuffle on big table |
| **Sort Merge Join** | Both sides large, equi-join | Good for large-large joins, requires sort + shuffle on both sides |
| **Shuffle Hash Join** | One side much smaller (but > broadcast threshold) | Shuffles both, builds hash table on smaller side |
| **Broadcast Nested Loop Join** | Non-equi join with small table (`BETWEEN`) | Broadcasts small side, loops through big side |
| **Cartesian Product** | No join condition | AVOID — explodes row count |

> Spark picks the strategy automatically based on table statistics. Run `ANALYZE TABLE <table> COMPUTE STATISTICS` to give Spark better info.

### 6. Spill to Disk — When & Why

| Aspect | Detail |
| --- | --- |
| **What is spill** | When a task's in-memory data exceeds its allocation, excess is written to local SSD |
| **Why it's bad** | Turns an in-memory operation into disk I/O — 10-100x slower |
| **Common causes** | Skewed joins (one key has millions of rows), huge sorts, insufficient memory |
| **Where to check** | Query Profile tab → look for "spill" metrics on each operator node |
| **How to fix** | (1) Reduce data volume with filters, (2) increase warehouse size, (3) fix skew |

### 7. Adaptive Query Execution (AQE)

| Feature | What It Does |
| --- | --- |
| **Dynamic partition coalescing** | Merges many tiny shuffle partitions into fewer, larger ones at runtime |
| **Dynamic join strategy switching** | If one side of a join turns out smaller than expected after a filter, switches to broadcast |
| **Skew join optimization** | Detects partitions with disproportionately many rows, splits them into sub-partitions |
| **Enabled by default** | YES on Databricks — no config needed |

#### LAYER 1: INGESTION (Source → Landing Zone)

**Choose your ingestion method:**

| Source Type | Best Ingestion | Why |
| --- | --- | --- |
| Files landing in cloud storage (CSV, JSON, Parquet) | **Auto Loader** (`cloudFiles`) | Incremental, exactly-once, schema evolution |
| Relational database (MySQL, Postgres, SQL Server) | **Lakeflow Connect** | Managed connector, no code, handles CDC |
| Kafka / Event Hub | **Structured Streaming** (Kafka source) | Native Spark, low latency |
| REST API / SaaS (Salesforce, HubSpot) | **Lakeflow Connect** | Pre-built connectors, scheduled |
| One-time bulk load | **COPY INTO** | SQL-only, idempotent, simple |

**Auto Loader — Production Pattern (File Notification Mode):**

```python
# Auto Loader reads new files incrementally from cloud storage
raw_df = (spark.readStream
    .format('cloudFiles')
    .option('cloudFiles.format', 'json')                  # Source format
    .option('cloudFiles.inferColumnTypes', 'true')         # Auto-detect types
    .option('cloudFiles.schemaLocation', '/mnt/schema/orders')  # Persist inferred schema
    .option('cloudFiles.useNotifications', 'true')         # Event-based (Azure Event Grid)
    .option('cloudFiles.schemaEvolutionMode', 'addNewColumns')  # Auto-add new columns
    .option('cloudFiles.rescuedDataColumn', '_rescued_data')    # Capture non-conforming data
    .load('abfss://raw@storage.dfs.core.windows.net/orders/')
)

# Add metadata columns for lineage
from pyspark.sql.functions import current_timestamp, input_file_name

bronze_df = (raw_df
    .withColumn('_ingestion_timestamp', current_timestamp())
    .withColumn('_source_file', input_file_name())
)

# Write to bronze streaming table
(bronze_df.writeStream
    .format('delta')
    .option('checkpointLocation', '/mnt/checkpoints/orders_bronze')
    .option('mergeSchema', 'true')         # Allow schema evolution on write
    .trigger(availableNow=True)            # Process all pending, then stop
    .table('bronze.orders_raw')
)
```

**Auto Loader — SQL-Only Alternative (inside SDP):**

```sql
-- Bronze streaming table with Auto Loader in SQL

AS SELECT
    *,
    current_timestamp() AS _ingestion_timestamp,
    _metadata.file_name AS _source_file,
    _metadata.file_modification_time AS _file_modified
FROM STREAM read_files(
    'abfss://raw@storage.dfs.core.windows.net/orders/',

);

**Auto Loader mode decision:**

| Aspect | Directory Listing | File Notification |
| --- | --- | --- |
| **How it finds new files** | Lists the directory each micro-batch | Cloud event triggers (Azure Event Grid / AWS SQS) |
| **Setup** | Zero config | Requires event subscription (Auto Loader can create it automatically) |
| **Latency** | Higher (depends on listing interval) | Lower (event-driven) |
| **Scale** | Good to \~10K new files/day | Millions of files/day |
| **Cost** | Higher at scale (listing is expensive) | Lower at scale (events are cheap) |
| **Best for** | Dev/test, small volumes | Production, high volume |

3. SCD Type 1 — Batch (MERGE)

The simplest CDC pattern. Source provides the latest state; you upsert into target.

-- SCD Type 1: Overwrite existing, insert new
MERGE INTO gold.customers AS target
USING staging.customers_daily AS source
  ON target.customer_id = source.customer_id
WHEN MATCHED AND (
  target.name != source.name OR
  target.email != source.email OR
  target.address != source.address
) THEN UPDATE SET
  target.name = source.name,
  target.email = source.email,
  target.address = source.address,
  target.updated_at = current_timestamp()
WHEN NOT MATCHED THEN INSERT (
  customer_id, name, email, address, updated_at
) VALUES (
  source.customer_id, source.name, source.email, source.address, current_timestamp()
);

Key points:

  • One row per customer in target (always latest)
  • The AND (target.name != source.name OR ...) avoids unnecessary updates when nothing changed
  • Idempotent — running twice with same data has no effect

4. SCD Type 2 — Batch (MERGE)

This is the complex pattern. Two operations in one MERGE: close the old row + insert the new row.

Target table schema:

CREATE TABLE gold.customers_history (
  customer_id INT,
  name STRING,
  email STRING,
  address STRING,
  effective_from TIMESTAMP,    -- When this version became active
  effective_to TIMESTAMP,      -- When this version was superseded (NULL = current)
  is_current BOOLEAN,          -- TRUE = latest version
  _merge_key INT               -- Used in MERGE trick (see below)
);

The SCD Type 2 MERGE pattern (exam favourite):

-- Step 1: Identify changed records
WITH changes AS (
  SELECT
    source.*,
    target.customer_id AS existing_id
  FROM staging.customers_daily source
  LEFT JOIN gold.customers_history target
    ON source.customer_id = target.customer_id
    AND target.is_current = TRUE
  WHERE
    target.customer_id IS NULL  -- New customers
    OR target.name != source.name
    OR target.email != source.email
    OR target.address != source.address  -- Changed customers
)

-- Step 2: MERGE with union trick to handle both close + insert
MERGE INTO gold.customers_history AS target
USING (
  -- Row 1: Match existing row (to close it)
  SELECT customer_id AS merge_key, customer_id, name, email, address
  FROM changes WHERE existing_id IS NOT NULL
  UNION ALL
  -- Row 2: NULL merge_key (will NOT match, so triggers INSERT)
  SELECT NULL AS merge_key, customer_id, name, email, address
  FROM changes
) AS source
  ON target.customer_id = source.merge_key AND target.is_current = TRUE

WHEN MATCHED THEN UPDATE SET
  target.is_current = FALSE,
  target.effective_to = current_timestamp()

WHEN NOT MATCHED THEN INSERT (
  customer_id, name, email, address,
  effective_from, effective_to, is_current, _merge_key
) VALUES (
  source.customer_id, source.name, source.email, source.address,
  current_timestamp(), NULL, TRUE, source.customer_id
);

How the MERGE trick works:

Row in UNION ALLmerge_keyMatches target?Action
Row 1 (existing customer)customer_id (real value)YES — matches current rowUPDATE: sets is_current = FALSE, effective_to = now()
Row 2 (all changes)NULLNO — NULL never matchesINSERT: new row with is_current = TRUE, effective_from = now()

Result: the old row is closed, and a new current row is inserted — all in one atomic MERGE.

| **Schema** | Auto-evolves with source |

**SCD Type 1 in SDP** — just change one parameter:

    target = 'customers_silver',
    source = 'customers_bronze',
    keys = ['customer_id'],
    sequence_by = col('event_timestamp'),
    stored_as_scd_type = 1,   # Overwrite, no history

```

### 9. Batch vs Streaming CDC — When to Use Which

| Aspect | Batch CDC (MERGE) | Streaming CDC (apply_changes / FLOW AUTO CDC) |
| --- | --- | --- |
| **Latency** | Minutes to hours (scheduled) | Seconds to minutes (continuous or triggered) |
| **Source** | Daily/hourly extract files, staging tables | Kafka, Auto Loader, Event Hub, Delta CDF |
| **Complexity** | You write the MERGE SQL manually | Framework handles dedup, ordering, SCD logic |
| **Out-of-order events** | You must handle (window + dedup) | Handled automatically by `sequence_by` |
| **Deletes** | Explicit in MERGE `WHEN MATCHED ... DELETE` | `apply_as_deletes` expression |
| **SCD Type 2** | Complex MERGE with UNION trick (see section 4) | One parameter: `stored_as_scd_type = 2` |
| **Exactly-once** | MERGE is idempotent if designed correctly | Checkpointing guarantees exactly-once |
| **Best for** | Simple upserts, legacy sources, small tables | High-volume CDC, real-time requirements, complex history |
| **Cost** | Lower (runs only when scheduled) | Higher (cluster running continuously) |
| **Exam tip** | Know the MERGE syntax by heart | Know `apply_changes` parameters and FLOW AUTO CDC syntax |

3. Data Modeling Strategies for 5 TB+ Tables

Strategy 1: Pre-Join at Silver (Eliminate Gold-Layer Shuffles)

The #1 mistake with large tables is joining them at the gold layer every run.

❌ BAD: Join 5 TB fact + dimensions every time gold refreshes
   gold.summary = JOIN(silver.transactions[5TB], silver.products, silver.stores)
   → 5 TB shuffle every single run

✅ GOOD: Pre-join once at silver, gold reads pre-joined table
   silver.transactions_enriched = JOIN(silver.transactions[5TB], products, stores)
   → Only new/changed data joined (incremental)
   gold.summary = AGGREGATE(silver.transactions_enriched)
   → Gold reads pre-joined data, no shuffle on 5 TB

Implementation:

-- Silver intermediate: pre-join fact + dimensions (run daily, incremental)
CREATE OR REFRESH STREAMING TABLE silver.transactions_enriched
CLUSTER BY (transaction_date, category_id, region)
AS SELECT
    t.*,
    p.product_name, p.category, p.subcategory, p.brand,
    s.store_name, s.region, s.state, s.format
FROM STREAM silver.transactions t
JOIN silver.products_current p ON t.product_id = p.product_id
JOIN silver.stores_current s ON t.store_id = s.store_id;

Now gold aggregations are simple scans with no joins:

CREATE OR REFRESH MATERIALIZED VIEW gold.daily_category_sales
AS SELECT
    transaction_date,
    region,
    category,
    SUM(amount) AS revenue,
    COUNT(*) AS transaction_count
FROM silver.transactions_enriched
GROUP BY transaction_date, region, category;

5. Incremental Processing Strategy (The Key to 5 TB+)

The #1 rule: Never reprocess the full 5 TB table when only 0.5% changed.

PatternFull ReprocessIncrementalSavings
Daily append (50 GB/day into 5 TB)Read 5 TB, write 5 TBRead 50 GB new, append100x less I/O
Daily MERGE (upsert)Scan 5 TB target + sourceCDF from silver (only changes) → MERGE50x less I/O
Dashboard refreshAggregate 5 TBMV auto-refresh (only changed partitions)20x less compute
Window function updateRecompute window over 5 TBRecompute only last 90 days, replace partition10x less compute

Incremental MERGE with CDF (the production pattern):

-- Gold table reads ONLY changed rows from silver via CDF
MERGE INTO gold.customer_360 AS target
USING (
    -- Only rows changed since last run (CDF)
    SELECT
        customer_id,
        SUM(amount) AS total_spend,
        MAX(transaction_date) AS last_purchase
    FROM table_changes('silver.transactions_enriched', 
        (SELECT MAX(last_processed_version) FROM gold._watermarks WHERE table_name = 'customer_360')
    )
    WHERE _change_type IN ('insert', 'update_postimage')
    GROUP BY customer_id
) AS source
    ON target.customer_id = source.customer_id
WHEN MATCHED THEN UPDATE SET
    target.total_spend = target.total_spend + source.total_spend,
    target.last_purchase = source.last_purchase
WHEN NOT MATCHED THEN INSERT *;

-- Update watermark
UPDATE gold._watermarks
SET last_processed_version = (SELECT MAX(version) FROM (DESCRIBE HISTORY silver.transactions_enriched))
WHERE table_name = 'customer_360';

Partition-scoped window refresh (REPLACE WHERE):

-- Instead of recomputing window over entire 5 TB:
-- Only recompute last 90 days and REPLACE those partitions
INSERT OVERWRITE silver.customer_rfm
SELECT
    customer_id,
    DATEDIFF(current_date(), MAX(transaction_date)) AS recency_days,
    COUNT(*) AS frequency_90d,
    SUM(amount) AS monetary_90d,
    NTILE(5) OVER (ORDER BY SUM(amount) DESC) AS monetary_quintile
FROM silver.transactions_enriched
WHERE transaction_date >= current_date() - 90
GROUP BY customer_id;

Step 1: Look at your top 10 queries (query history)
Step 2: Extract all WHERE and JOIN ON columns
Step 3: Rank by frequency of use
Step 4: Pick top 2-4 (diminishing returns after 4)
Step 5: Put highest-cardinality column LAST

  WHERE transaction_date = ...        → used in 95% of queries  → Column 1
  WHERE region = ...                  → used in 60% of queries  → Column 2

  JOIN ON customer_id = ...           → used in 30% of queries  → Column 4 (highest cardinality)

  Result: CLUSTER BY (transaction_date, region, category, customer_id)

## Large-Scale Solution Design (5 TB+ Tables, Complex Transformations)

### 1. The Core Problem at Scale

When tables exceed 5 TB with heavy joins, aggregations, and window functions, you hit problems that don't exist at smaller scale:

| Problem | Why It Happens at 5 TB+ | Impact |
| --- | --- | --- |
| **Shuffle explosion** | JOIN of 5 TB x 2 TB = up to 10 TB shuffled across network | Hours of runtime, potential OOM |
| **Spill to disk** | Single executor can't hold a skewed partition in memory | 10-100x slower than in-memory |
| **Small file problem** | Daily appends over years = millions of tiny files | File listing alone takes minutes |
| **Skewed partitions** | One join key (e.g., a B2B mega-customer) has 100M rows while median has 50 | One task runs 1000x longer than others |
| **Stale statistics** | Optimizer thinks table is 100 MB, picks broadcast join on a 5 TB table | Wrong join strategy = catastrophic |
| **Checkpoint bloat** | Streaming checkpoint metadata grows with table size | Restart takes 30+ minutes |
| **Concurrent writes** | Multiple pipelines writing to same 5 TB table | `ConcurrentAppendException`, file conflicts |

### 3. Data Modeling Strategies for 5 TB+ Tables

#### Strategy 1: Pre-Join at Silver (Eliminate Gold-Layer Shuffles)

The #1 mistake with large tables is joining them at the gold layer every run.

```
❌ BAD: Join 5 TB fact + dimensions every time gold refreshes
   gold.summary = JOIN(silver.transactions[5TB], silver.products, silver.stores)
   → 5 TB shuffle every single run

✅ GOOD: Pre-join once at silver, gold reads pre-joined table
   silver.transactions_enriched = JOIN(silver.transactions[5TB], products, stores)
   → Only new/changed data joined (incremental)
   gold.summary = AGGREGATE(silver.transactions_enriched)
   → Gold reads pre-joined data, no shuffle on 5 TB
```

**Implementation:**
```sql
-- Silver intermediate: pre-join fact + dimensions (run daily, incremental)
CREATE OR REFRESH STREAMING TABLE silver.transactions_enriched
CLUSTER BY (transaction_date, category_id, region)
AS SELECT
    t.*,
    p.product_name, p.category, p.subcategory, p.brand,
    s.store_name, s.region, s.state, s.format
FROM STREAM silver.transactions t
JOIN silver.products_current p ON t.product_id = p.product_id
JOIN silver.stores_current s ON t.store_id = s.store_id;
```

Now gold aggregations are simple scans with no joins:
```sql
CREATE OR REFRESH MATERIALIZED VIEW gold.daily_category_sales
AS SELECT
    transaction_date,
    region,
    category,
    SUM(amount) AS revenue,
    COUNT(*) AS transaction_count
FROM silver.transactions_enriched
GROUP BY transaction_date, region, category;
```

### 4. Handling Expensive Transformations at Scale

#### 4a. Large JOINs (5 TB x 2 TB)

| Technique | When | How | Impact |
| --- | --- | --- | --- |
| **Broadcast small side** | Dimension < 1 GB after filter | `/*+ BROADCAST(dim) */` or Auto Loader infers | Eliminates shuffle on large side entirely |
| **Pre-filter before join** | Many rows in fact don't match dimension | `WHERE transaction_date >= current_date - 30` before join | Reduces data entering shuffle by 90%+ |
| **Bucket/cluster on join key** | Same two tables joined repeatedly | Both tables `CLUSTER BY (join_key)` | Data pre-sorted on same key = local join, no shuffle |
| **Pre-join at silver** | Fact + dimension joined by every downstream query | Materialize the joined result (see Strategy 1) | Gold queries become scan-only |
| **Salted join for skew** | One join key has 100M rows, median has 50 | Append random salt (0-9) to skewed key, join in two stages | Splits hot partition into 10 equal ones |
| **Incremental join** | Only 1% of data changes daily | Join only new/changed partitions, MERGE into target | Process 50 GB/day instead of 5 TB |

**Broadcast hint (exam-critical):**
```sql
-- Force broadcast on small dimension (< 1 GB)
SELECT /*+ BROADCAST(p) */
    t.transaction_date,
    p.category,
    SUM(t.amount) AS revenue
FROM silver.transactions t        -- 5 TB
JOIN silver.products_current p    -- 50 MB → broadcast to all executors
    ON t.product_id = p.product_id
GROUP BY 1, 2;
```

**Salted join for skew:**
```sql
-- Problem: customer_id = 'WHOLESALE_CORP' has 100M rows, causes 1 task to run 100x longer
-- Solution: Salt the skewed key

-- Step 1: Add salt to large table
WITH salted_transactions AS (
    SELECT *, FLOOR(RAND() * 10) AS salt
    FROM silver.transactions
    WHERE transaction_date >= current_date() - 30
),
-- Step 2: Explode small table to match all salts
exploded_customers AS (
    SELECT c.*, s.salt
    FROM silver.customers_current c
    CROSS JOIN (SELECT EXPLODE(SEQUENCE(0, 9)) AS salt) s
)
-- Step 3: Join on key + salt (distributes 100M rows across 10 partitions)
SELECT
    t.customer_id,
    c.segment,
    SUM(t.amount) AS total_spend
FROM salted_transactions t
JOIN exploded_customers c
    ON t.customer_id = c.customer_id
    AND t.salt = c.salt
GROUP BY 1, 2;
```

#### 4b. Large Aggregations (GROUP BY on 5 TB)

| Technique | When | How |
| --- | --- | --- |
| **Two-stage aggregation** | High-cardinality GROUP BY | Aggregate per partition first, then merge |
| **Pre-filter aggressively** | Only need last 30 days of 3 years | `WHERE date >= current_date - 30` before GROUP BY |
| **Partial aggregation at silver** | Same aggregation used by multiple gold tables | Create an intermediate aggregate table |
| **Approximate functions** | Exact count isn't needed | `APPROX_COUNT_DISTINCT()` is 10x faster than `COUNT(DISTINCT)` |
| **Cluster by GROUP BY columns** | Same GROUP BY query runs daily | `CLUSTER BY (group_col_1, group_col_2)` = data pre-sorted |

```sql
-- APPROX_COUNT_DISTINCT: 10x faster, ~2% error margin
SELECT
    transaction_date,
    region,
    SUM(amount) AS revenue,
    APPROX_COUNT_DISTINCT(customer_id) AS approx_unique_customers  -- 10x faster
FROM silver.transactions_enriched
WHERE transaction_date >= current_date() - 90
GROUP BY 1, 2;
```

#### 4c. Window Functions on 5 TB

Window functions are expensive because `PARTITION BY` requires a shuffle, then `ORDER BY` requires a sort within each partition.

| Technique | When | How |
| --- | --- | --- |
| **Narrow the window scope** | Only need recent data | `WHERE date >= current_date - 90` before window |
| **Pre-compute and store** | Same window used by multiple consumers | Materialize the window result as a gold table |
| **Cluster on PARTITION BY key** | Same partition key used repeatedly | `CLUSTER BY (partition_key)` = no shuffle needed |
| **Replace with aggregate** | `ROW_NUMBER() ... = 1` is just a dedup | Use `QUALIFY` or `GROUP BY` + `MAX()` instead |
| **Incremental windows** | Rolling 7-day average updated daily | Maintain state: subtract day 8, add day 1 |

**Pre-compute expensive window at silver:**
```sql
-- Pre-compute RFM scores at silver (run daily, store result)
CREATE OR REPLACE TABLE silver.customer_rfm AS
SELECT
    customer_id,
    -- Recency: days since last purchase
    DATEDIFF(current_date(), MAX(transaction_date)) AS recency_days,
    -- Frequency: number of purchases in 90 days
    COUNT(*) AS frequency_90d,
    -- Monetary: total spend in 90 days
    SUM(amount) AS monetary_90d,
    -- Ranking
    NTILE(5) OVER (ORDER BY SUM(amount) DESC) AS monetary_quintile,
    NTILE(5) OVER (ORDER BY COUNT(*) DESC) AS frequency_quintile,
    NTILE(5) OVER (ORDER BY DATEDIFF(current_date(), MAX(transaction_date))) AS recency_quintile
FROM silver.transactions_enriched
WHERE transaction_date >= current_date() - 90
GROUP BY customer_id;
```

Now gold dashboards query `silver.customer_rfm` (small table) instead of windowing 5 TB every time.

**Replace ROW_NUMBER with QUALIFY:**
```sql
-- Instead of subquery + ROW_NUMBER = 1
-- ❌ Slower:
SELECT * FROM (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY updated_at DESC) AS rn
    FROM silver.customers
) WHERE rn = 1;

-- ✅ Faster (QUALIFY, Databricks-native):
SELECT *
FROM silver.customers
QUALIFY ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY updated_at DESC) = 1;
```

### 5. Incremental Processing Strategy (The Key to 5 TB+)

The #1 rule: **Never reprocess the full 5 TB table when only 0.5% changed.**

| Pattern | Full Reprocess | Incremental | Savings |
| --- | --- | --- | --- |
| Daily append (50 GB/day into 5 TB) | Read 5 TB, write 5 TB | Read 50 GB new, append | 100x less I/O |
| Daily MERGE (upsert) | Scan 5 TB target + source | CDF from silver (only changes) → MERGE | 50x less I/O |
| Dashboard refresh | Aggregate 5 TB | MV auto-refresh (only changed partitions) | 20x less compute |
| Window function update | Recompute window over 5 TB | Recompute only last 90 days, replace partition | 10x less compute |

**Incremental MERGE with CDF (the production pattern):**
```sql
-- Gold table reads ONLY changed rows from silver via CDF
MERGE INTO gold.customer_360 AS target
USING (
    -- Only rows changed since last run (CDF)
    SELECT
        customer_id,
        SUM(amount) AS total_spend,
        MAX(transaction_date) AS last_purchase
    FROM table_changes('silver.transactions_enriched', 
        (SELECT MAX(last_processed_version) FROM gold._watermarks WHERE table_name = 'customer_360')
    )
    WHERE _change_type IN ('insert', 'update_postimage')
    GROUP BY customer_id
) AS source
    ON target.customer_id = source.customer_id
WHEN MATCHED THEN UPDATE SET
    target.total_spend = target.total_spend + source.total_spend,
    target.last_purchase = source.last_purchase
WHEN NOT MATCHED THEN INSERT *;

-- Update watermark
UPDATE gold._watermarks
SET last_processed_version = (SELECT MAX(version) FROM (DESCRIBE HISTORY silver.transactions_enriched))
WHERE table_name = 'customer_360';
```

**Partition-scoped window refresh (REPLACE WHERE):**
```sql
-- Instead of recomputing window over entire 5 TB:
-- Only recompute last 90 days and REPLACE those partitions
INSERT OVERWRITE silver.customer_rfm
SELECT
    customer_id,
    DATEDIFF(current_date(), MAX(transaction_date)) AS recency_days,
    COUNT(*) AS frequency_90d,
    SUM(amount) AS monetary_90d,
    NTILE(5) OVER (ORDER BY SUM(amount) DESC) AS monetary_quintile
FROM silver.transactions_enriched
WHERE transaction_date >= current_date() - 90
GROUP BY customer_id;
```

**How to choose clustering columns (decision process):**

```
Step 1: Look at your top 10 queries (query history)
Step 2: Extract all WHERE and JOIN ON columns
Step 3: Rank by frequency of use
Step 4: Pick top 2-4 (diminishing returns after 4)
Step 5: Put highest-cardinality column LAST

Example:
  WHERE transaction_date = ...        → used in 95% of queries  → Column 1
  WHERE region = ...                  → used in 60% of queries  → Column 2
  WHERE category = ...                → used in 40% of queries  → Column 3
  JOIN ON customer_id = ...           → used in 30% of queries  → Column 4 (highest cardinality)

  Result: CLUSTER BY (transaction_date, region, category, customer_id)
```

### 9. Anti-Patterns to Avoid at 5 TB+

| # | Anti-Pattern | Why It's Bad | Correct Pattern |
| --- | --- | --- | --- |
| 1 | JOIN 5 TB x 2 TB at gold layer every run | 7 TB shuffled daily | Pre-join at silver, gold reads pre-joined table |
| 2 | `SELECT *` on 5 TB table | Reads all 100+ columns even if you need 5 | Always `SELECT` only needed columns |
| 3 | Full table reprocess daily | Re-reading 5 TB when 50 GB changed | Incremental with CDF + watermarks |
| 4 | `COUNT(DISTINCT x)` on 5 TB | Requires global shuffle of entire column | `APPROX_COUNT_DISTINCT(x)` for dashboards |
| 5 | Window function on unbounded data | `OVER (PARTITION BY ... ORDER BY ...)` on 5 TB | Scope to rolling window: `WHERE date >= current_date - 90` |
| 6 | No `ANALYZE TABLE` on gold | Optimizer guesses join strategy wrong | `ANALYZE TABLE ... COMPUTE STATISTICS` after every major load |
| 7 | Skipped `OPTIMIZE` for months | 500K small files, scans take 10 min | Weekly OPTIMIZE, monitor with `DESCRIBE DETAIL` |
| 8 | `ORDER BY` in intermediate CTE | Sorts 5 TB for no reason (downstream ignores order) | Only `ORDER BY` in final output or `LIMIT` queries |
| 9 | Storing aggregates as views (not MVs) | 5 TB scanned every dashboard refresh | Use Materialized Views for repeated aggregations |
| 10 | Single monolithic job | 6-hour job fails at hour 5, restart from zero | DAG with stages: retry per task, not per pipeline |
| 11 | Same cluster for ingest + serve | ETL hogs all resources, dashboards timeout | Separate compute: Job Cluster for ETL, SQL WH for serving |
| 12 | Joining on CAST/function | `INT(a.col) = INT(b.col)` prevents pushdown | Store join keys in the correct type at silver layer |

  THEN UPDATE SET *
WHEN NOT MATCHED
  THEN INSERT *;

#### Problem 1: Silent Data Loss in a Medallion Pipeline

**Scenario you describe:**
> "Our silver layer table was showing 15% fewer records than bronze for the same day. No errors in the job logs — the pipeline reported SUCCESS every night. The business noticed revenue numbers were off after 3 weeks."

**Root Cause:**
A schema change upstream added a new `currency_code` column with `NULL` values for the first 2 weeks. The bronze-to-silver transformation had an `INNER JOIN` to a currency reference table on `currency_code`. NULLs don't match in inner joins — so 15% of rows silently dropped.

**How you debugged it:**

| Step | Action | Tool/Technique |
| --- | --- | --- |
| 1 | Compared bronze vs silver row counts by day using Delta Time Travel | `SELECT count(*) FROM bronze.orders VERSION AS OF 42` |
| 2 | Found the drop started on a specific date — checked `DESCRIBE HISTORY bronze.orders` | Delta transaction log showed a schema evolution merge on that date |
| 3 | Profiled NULL rates per column on bronze | `SELECT count_if(currency_code IS NULL) / count(*) FROM bronze.orders` |
| 4 | Identified the INNER JOIN as the filter | Changed to `LEFT JOIN` + COALESCE for default currency |
| 5 | Backfilled silver from bronze using Time Travel | Delta kept all bronze versions — no data was actually lost |

**What makes this principal-level:**
- You built a **data quality monitoring framework** after this: row count reconciliation between layers with automated alerts
- You introduced **schema evolution policies**: any new nullable column triggers a review before silver transformation changes
- You added **expectations/assertions** at the silver layer: `CONSTRAINT valid_currency EXPECT (currency_code IS NOT NULL) ON VIOLATION DROP ROW` with logging

#### Problem 2: Job Succeeds But Takes 8 Hours Instead of 40 Minutes

**Scenario you describe:**

**Root Cause:**

#### Problem 3: Concurrent Writes Causing ConcurrentAppendException

**Scenario you describe:**
> "Two teams were writing to the same gold table — one via a streaming job (append) and another via a nightly MERGE. Every few days the MERGE failed with `ConcurrentAppendException`. The streaming job was critical and couldn't be paused."

**Root Cause:**
Delta Lake's optimistic concurrency control detected that both operations modified overlapping file ranges. The MERGE was rewriting files that the streaming append had just written to.

**Solution:**

| Approach | Detail |
| --- | --- |
| **Partitioned isolation** | Restructured the table with `PARTITIONED BY (source_system)` — streaming writes to partition `source_system='realtime'`, MERGE only touches `source_system='batch'` |
| **Write serialization** | For the overlap period, used Delta's `delta.isolationLevel = WriteSerializable` (less strict than Serializable) |
| **Idempotent writes** | Made the streaming job idempotent using `foreachBatch` with MERGE instead of append — so retries are safe |
| **Architecture change** | Long-term: separated into two tables + a UNION ALL view for consumers. Eliminated contention entirely |

**What makes this principal-level:**
- You understood Delta's **MVCC (multi-version concurrency control)** at the protocol level — conflict detection is file-level, not row-level
- You evaluated multiple solutions and chose based on tradeoffs (partition isolation is simple but adds query complexity; separate tables are cleanest but require consumer changes)
- You documented a **write contention playbook** for the team

#### Problem 4: OOM (Out of Memory) on a Join That Used to Work

**Scenario you describe:**
> "A daily report query that joined a 500M-row transaction table with a 'small' reference table started failing with OOM. Nothing in the query changed. The job had run fine for a year."

**Root Cause:**
The "small" reference table had grown from 8 MB to 15 MB over the year (new products added daily). Spark's broadcast threshold is 10 MB by default. When the table crossed 10 MB, Spark switched from **Broadcast Hash Join** (small table copied to all executors) to **Sort Merge Join** (both tables shuffled). The shuffle of the 500M-row table didn't fit in memory.

**How you debugged it:**

| Step | Action | Finding |
| --- | --- | --- |
| 1 | `EXPLAIN EXTENDED` on the failing query | Join strategy: SortMergeJoin (was BroadcastHashJoin last month) |
| 2 | `DESCRIBE DETAIL reference_table` | sizeInBytes: 15.2 MB (crossed 10 MB threshold) |
| 3 | Query Profile | 18 GB spill to disk on the sort phase of SMJ |
| 4 | Added broadcast hint: `/*+ BROADCAST(ref) */` | Query succeeded in 3 minutes |
| 5 | Long-term: `ANALYZE TABLE reference_table COMPUTE STATISTICS` | Ensured optimizer always has fresh stats |

**What makes this principal-level:**
- You didn't just add a hint — you built a **table growth monitoring alert** that flags when reference tables approach the broadcast threshold
- You created a policy: all reference/dimension tables must have `ANALYZE TABLE` as a post-write step
- You evaluated raising `spark.sql.autoBroadcastJoinThreshold` to 50 MB but rejected it because it would mask future issues with genuinely large tables

#### Problem 5: Data Skew Causing One Task to Run 100x Longer

**Scenario you describe:**
> "A GROUP BY aggregation on customer_id had 200 tasks finishing in 5 seconds each, but 1 task took 45 minutes. The job SLA was 10 minutes. Total data was only 50 GB."

**Root Cause:**
One `customer_id` (a B2B wholesale account) had 800M transactions while the median customer had 50. That single key landed in one partition, creating a **skewed partition** 1000x larger than the rest.

**Solution:**

| Technique | How It Works | When to Use |
| --- | --- | --- |
| **AQE Skew Join** | Spark detects the large partition and auto-splits it into sub-partitions | First thing to try — enabled by default on Databricks |
| **Salting** | Append a random number (0-9) to the skewed key, aggregate in two stages: first by `(key, salt)`, then by `key` | When AQE isn't enough or for non-join skew |
| **Isolate and union** | Process the skewed key separately with a broadcast join, UNION ALL with the rest | When one key dominates and needs special logic |
| **Pre-aggregate** | Reduce the 800M rows for that customer to daily summaries before joining | Best long-term solution |

**What makes this principal-level:**
- You built a **skew detection query** that runs pre-flight before expensive jobs: `SELECT key, count(*) as cnt FROM table GROUP BY key HAVING cnt > 10 * (SELECT percentile(cnt, 0.5) FROM (SELECT count(*) cnt FROM table GROUP BY key))`
- You designed the pipeline to handle skew architecturally (pre-aggregation at silver layer) rather than relying on runtime hints

#### Problem 6: Streaming Job Silently Stops Processing New Data

**Scenario you describe:**
> "Our Structured Streaming job showed as RUNNING in the Spark UI. No errors. But the watermark hadn't advanced in 6 hours — no new data was being processed. The source Kafka topic was actively receiving events."

#### Problem 7: Redesigning a Monolithic ETL into Medallion Architecture

**Scenario you describe:**
> "Inherited a 4,000-line SQL script that ran as a single job for 6 hours. It read from 15 source systems, applied 200+ business rules, and wrote to 8 reporting tables. Any failure meant re-running the entire 6-hour job. The business wanted 1-hour SLA."

**Solution — Medallion with Dependency DAG:**

```
Bronze (raw ingestion)        Silver (cleaned/conformed)       Gold (business-ready)
┌─────────────────┐          ┌────────────────────┐          ┌──────────────────┐
│ 15 source tables │ ──CDC──▶ │ Deduplicated       │ ──JOIN──▶│ Revenue summary  │
│ (append-only,    │          │ Type-cast          │          │ Customer 360     │
│  schema-on-read) │          │ Null-handled       │          │ Product metrics  │
│                  │          │ Partitioned by date│          │ (pre-aggregated) │
└─────────────────┘          └────────────────────┘          └──────────────────┘
     5 min each                   10 min each                    15 min each
     Independent                  Depends on bronze              Depends on silver
     Parallel                     Parallel within layer          Parallel within layer
```

| Design Decision | Why |
| --- | --- |
| **Bronze = append-only, raw** | Source of truth. Never loses data. Can replay from here. |
| **Silver = cleaned, conformed** | Business rules applied once. Shared across gold tables. Failures here don't require re-ingestion. |
| **Gold = pre-aggregated, denormalized** | Optimized for query speed. Materialized views where possible. |
| **Each layer is a separate job task** | Failure in gold doesn't re-run bronze/silver. Retry is minutes, not hours. |
| **Dependency DAG** | Bronze tasks run in parallel → silver waits for its bronze → gold waits for its silver |

**Result:** 6-hour monolith → 45-minute DAG with per-task retry. SLA met.

**What makes this principal-level:**
- You didn't just split the SQL — you redesigned the **data model** so each layer is independently testable and replayable
- You introduced **data contracts** between layers: silver guarantees non-null keys, valid dates, deduplication
- You added **circuit breakers**: if bronze row count deviates >20% from yesterday, silver doesn't run — prevents bad data propagation

#### Problem 10: Implementing Incremental Processing with MERGE

**Scenario you describe:**
> "The team was doing `INSERT OVERWRITE` of the entire 500 GB table every night — recomputing all history. It took 4 hours and cost $800/run. Only 0.1% of rows changed daily."

**Solution:**

```sql
-- Before: Full rewrite (4 hours, $800)
INSERT OVERWRITE TABLE gold.customers
SELECT * FROM silver.customers;

-- After: Incremental MERGE (8 minutes, $12)
MERGE INTO gold.customers AS target
USING (
  SELECT * FROM silver.customers
  WHERE _commit_timestamp > (SELECT max(last_updated) FROM gold.customers_watermark)
) AS source
ON target.customer_id = source.customer_id
WHEN MATCHED AND source.updated_at > target.updated_at
  THEN UPDATE SET *
WHEN NOT MATCHED
  THEN INSERT *;
```

| Aspect | INSERT OVERWRITE | MERGE (Incremental) |
| --- | --- | --- |
| Rows processed | 500M (all) | 500K (changed only) |
| Duration | 4 hours | 8 minutes |
| Cost per run | $800 | $12 |
| Monthly cost | $24,000 | $360 |
| Deletion vectors | Not applicable | Enabled — avoids full file rewrite for updates |

**Additional optimizations applied:**

| Technique | Detail |
| --- | --- |
| **Deletion Vectors** | `ALTER TABLE gold.customers SET TBLPROPERTIES ('delta.enableDeletionVectors' = true)` — MERGE updates mark rows as deleted instead of rewriting entire files |
| **Change Data Feed (CDF)** | Enabled on silver table — `ALTER TABLE silver.customers SET TBLPROPERTIES ('delta.enableChangeDataFeed' = true)` — so MERGE source reads only changed rows |
| **Watermark table** | Tracks last processed `_commit_version` per table — enables exactly-once incremental processing |
| **OPTIMIZE post-MERGE** | Scheduled weekly OPTIMIZE to compact the small files created by incremental MERGEs |

**What makes this principal-level:**
- You designed an **incremental processing framework** reusable across 40+ tables, not a one-off fix
- You combined CDF + MERGE + deletion vectors — three Delta features working together
- You handled edge cases: late-arriving data, schema evolution, idempotent reruns
