Chapter 01

Principal Mental Model

core

Principal Data Engineering starts with decisions, not products

A Principal Engineer must be able to move across six levels: understand → build → operate → design → decide → influence. Tools change; the decision framework survives.

Understand

Explain the concept in plain English, know what problem it solves, and know its limits.

Engineer

Build for retries, change, scale, observability, correctness and maintainability—not only the happy path.

Lead

Turn ambiguous business goals into NFRs, alternatives, trade-offs, standards and measurable outcomes.

Principal lens

For every design ask: What is the business SLA? What is the failure model? What is the replay boundary? What is the source of truth? Where does cost scale? Who owns the contract? What changes at 5× volume?

Architecture decision frame

Business outcome → Functional requirements → NFRs → Data characteristics → Constraints → Options → Trade-offs → Decision/ADR → Operability → Evidence

Interview articulation

“I start by clarifying scale, latency, correctness, availability, recovery and ownership. I then compare the simplest viable architecture against alternatives, make the trade-offs explicit, and design the operational model before selecting products.”

Chapter 03

Storage, Micro-partitions & Query Lifecycle

snowflake

Why Snowflake performance starts with pruning

Snowflake stores table data in immutable, columnar micro-partitions and maintains metadata about them. Good pruning reduces data scanned; poor pruning forces more work before warehouse size can help.

Query lifecycle mental model

Parse/auth → optimize → identify partitions → scan/prune → join/aggregate/sort → spill if needed → result → cache opportunities
Symptom: a query grew from 25 s to 4 min after a year of data growth.
Do not start with: “resize from Medium to XL.”
Investigate: partitions scanned, pruning, join explosion, spill, skew-like fan-out, concurrency, result/cache behavior, selective predicates, clustering/search optimization suitability.

Clustering vs Search Optimization vs Materialized View

MechanismBest fitTrade-off
ClusteringLarge tables with recurrent range/equality pruning needs and degraded natural clusteringMaintenance cost and not always needed
Search OptimizationHighly selective lookups/search patterns where standard pruning is insufficientStorage/maintenance cost; target specific workloads
Materialized ViewRepeated expensive deterministic computation with strong reuseRefresh/storage cost and eligibility constraints
Principal lens

Performance is an economics problem. Tune the query shape and data access pattern first; buy larger compute only when the bottleneck is genuinely compute/concurrency.

Chapter 04

Ingestion: Batch, CDC & Streaming

de

Choose ingestion from the business freshness requirement

Batch, CDC and streaming are not maturity levels. They are latency/cost/complexity choices.

PatternUse whenAvoid whenTypical failure concern
BatchMinute/hour/day freshness is enough; files or extract windows are naturalBusiness truly needs seconds-level reactionpartial files, reruns, duplicate loads
CDCNeed changed rows without re-reading the whole sourceSource semantics are unreliable or history can be reconstructed cheaplyLSN/offset gaps, DDL drift, delete semantics
StreamingContinuous events and low latency have measurable valueOnly dashboard refresh cadence is “real time”ordering, duplicates, poison events, backpressure

Core concepts that survive tool changes

idempotencywatermarkcheckpointoffsetreplaybackfilllate dataschema evolutionat-least-oncedata contract

Snowflake options

Batch: stages + COPY INTO / orchestrated load. Continuous files: Snowpipe. Low-latency event ingest: Snowpipe Streaming. Database CDC: evaluate Openflow connectors, Kafka/Debezium/GoldenGate or existing enterprise integration.

Principal lens

Define the replay boundary before building the happy path. The architecture is not complete until you can prove how to recover from a gap, duplicate, corrupted batch, schema change and downstream partial publish.

Chapter 05

Streams, Tasks & Dynamic Tables

snowflake

Three different concerns

Streams expose change tracking state for tables/views. Tasks schedule/chain execution. Dynamic Tables declaratively maintain query results toward a target freshness. Do not treat them as synonyms.

NeedLikely fitReason
Run arbitrary procedural SQL on a schedule/dependency graphTasksExplicit orchestration/control
Consume row-level changes from a source objectStreamsChange tracking semantics
Maintain derived tables based on declarative query + freshness goalDynamic TablesPlatform manages refresh planning
Cross-platform workflow with APIs, SAP, ML, notificationsExternal orchestrator may remain betterBroader control plane
Design test: If a pipeline has 40 SQL transforms but no external side effects, compare Dynamic Tables with dbt+orchestrator. If it also calls APIs, coordinates source extracts, runs ML and publishes files, keep orchestration boundaries explicit.
Principal lens

Prefer declarative maintenance when it reduces operational code without obscuring SLA, cost, recovery or ownership. Standardize a small number of blessed patterns.

Chapter 06

Data Modelling & SCD

model

Model from business grain, not from source tables

Start every fact design by stating the grain in one sentence. Example: “one row per store × item × trading day.” Then determine facts, dimensions, late-arriving behavior and history.

Kimball, Data Vault, Medallion, Semantic layer

PatternProblem it solvesPrincipal caution
KimballBusiness-facing analytics with conformed facts/dimensionsGet grain and conformance right; avoid source-shaped marts
Data Vault 2.0Auditable historized integration across changing sourcesExtra modelling/joins; use where lineage/history justify complexity
MedallionLayered refinement/quality responsibilitiesLayer names do not replace contracts or domain modelling
Semantic layerReusable governed business metrics/dimensionsAvoid duplicating metric logic in dashboards and agents

SCD decision

Type 1: overwrite when only current truth matters. Type 2: preserve historical versions when analysis must reproduce “as-was” state. Types 0/3/4/6 are useful patterns but far less universally applicable.

-- Simplified SCD2 idea
WHEN MATCHED AND target.record_hash <> source.record_hash
  THEN expire current version
WHEN NOT MATCHED OR changed
  THEN insert new version with effective_start_dt, effective_end_dt, is_current
Principal lens

SCD2 is not “the safe default.” History multiplies storage, merge complexity and semantic ambiguity. Preserve only history that has a business/audit requirement.

Chapter 07

Reliability, DQ, Metadata & Observability

ops

A pipeline is a service

Production data engineering needs explicit SLOs: freshness, completeness, correctness, availability and recovery.

Freshness

How late can data be before the consumer outcome is impaired?

Correctness

Which invariants prove the dataset is usable—not merely non-empty?

Recovery

How quickly can we restore service and how much data can be lost?

Standard metadata

Use metadata because it supports operations, lineage or audit—not because every table needs 15 identical columns. Common fields include source_system, record_source, load_ts, pipeline_run_id, batch_id, file_name, record_hash and SCD effective dates.

SignalExample checkAction
Volumetoday within expected range vs seasonalityhold publish if breach is material
Freshnessmax source event time / load timealert based on consumer SLA
Reconciliationsource/control total vs targetquarantine/replay affected batch
Schemacontract-compatible changeauto-accept additive; gate breaking changes
Chapter 08

Performance Engineering & FinOps

ops

Tune cost per useful outcome

Snowflake cost is not just warehouse size. It includes duration, concurrency, serverless/managed features, storage/retention, replication, search services and AI usage.

Diagnosis order

Workload/SLA → Query profile → Data scanned/pruned → joins/spill → concurrency/queuing → warehouse policy → special services → cost attribution
ProblemFirst responseBad reflex
Slow single queryprofile + pruning + join shapealways scale warehouse
Many users queuedconcurrency isolation/multi-cluster analysisrewrite every query first
Idle creditsauto-suspend, workload scheduling, consolidationsmaller warehouse with longer runtime
Expensive point lookupsaccess pattern + search optimization suitabilitycluster everything
Principal lens

Every optimization has a second-order effect. A feature that saves 30 seconds but adds permanent maintenance cost may be a net loss. Baseline, change one thing, measure, and attribute spend to domain/workload.

Chapter 09

Security, Governance & Data Products

gov

Govern through reusable policy

Design role hierarchy, ownership, tagging/classification, masking, row access, sharing, lineage and contracts as platform capabilities. Avoid per-table manual exceptions.

Data product contract

Owner + purpose + schema + semantics + quality SLO + freshness SLO + access policy + change policy + lineage + support model

RBAC vs ABAC-style policy

Use roles for stable responsibilities and policy/tag-driven approaches where access should follow attributes/classification. The exact implementation is platform-specific; the architecture principle is least privilege with scalable policy inheritance.

Principal lens

Governance that only creates tickets will be bypassed. Build paved roads: automated classification, standard tags, policy templates, self-service access paths, lineage and evidence.

Chapter 11

Modern Snowflake & Open Data (2026)

modern

What deserves attention in 2026

This chapter separates durable architecture shifts from “new feature” noise. Validate preview/GA status in official release notes before production commitments.

Iceberg & open interoperability

Snowflake has expanded Iceberg capabilities, including Snowflake-managed storage options, ADLS Gen2 support and external-engine write interoperability. Principal question: who owns catalog, metadata, writes, compaction and disaster recovery?

Openflow CDC

Native/open integration options can simplify Oracle and SQL Server CDC. Compare connector maturity, licensing, replay guarantees, enterprise observability and existing Kafka/GoldenGate standards.

Dynamic Tables evolution

Recent capabilities improve refresh control and adaptive behavior. Use declarative refresh where it removes orchestration code without sacrificing transparency.

Organization & adaptive compute

Organization-level management and newer compute capabilities can change platform operating models. Treat them as governance/cost design inputs, not isolated features.

Chapter 13

System Design & Principal Architecture Reviews

principal

How to answer a system-design problem

  1. Clarify business outcome and consumers.
  2. Quantify scale: records/bytes, peak, growth, concurrency.
  3. Set latency/freshness and correctness requirements.
  4. Define RTO/RPO, security, residency and compliance.
  5. Describe source behavior and change semantics.
  6. Present 2–3 viable architectures.
  7. Select one and explicitly reject the others.
  8. Cover failure/replay/backfill.
  9. Cover observability, governance and cost.
  10. Explain evolution at 5× scale.

Natural principal-level answer opener

“Before choosing Snowpipe, Kafka or batch, I’d separate the consumers by freshness. If only store availability needs sub-two-minute data while finance is T+1, I won’t impose streaming complexity on the whole estate.”
Principal lens

The strongest design answer is rarely the one with the most services. It is the one whose complexity matches the requirements and whose failure/recovery story is credible.

Project laboratory

Large-enterprise architecture projects

These are not toy tutorials. Each project forces you to choose ingestion, modelling, reliability, governance, performance and operating patterns. The reference answer is one defensible design—not the only possible design.

P1 — Enterprise Retail Data Platform Modernisation
Batch • CDC • Streaming • Snowflake • Databricks • Governance

Requirements

10–30 TB/day; Oracle ERP, SAP, POS, loyalty, APIs and Kafka; thousands of tables; BI + ML + operational consumers.

Reference architecture

Sources → ingestion zone → raw/bronze → conformed/silver → dimensional/data products → BI/semantic/AI. Separate low-latency paths only where SLA requires them.

Trade-off review

OptionBenefitCost/RiskDecision
Full-load everythingSimple initiallyNetwork/compute waste; poor recovery at scaleReject except small/static sources
CDC all sourcesEfficient change captureSource/connector complexity; history semanticsUse selectively for mutable high-volume systems
Hybrid batch + CDC + streamingMatches SLA by domainMore patterns to governPreferred enterprise approach

Failure & recovery

Design batch IDs/offsets, immutable landing where possible, reconciliation totals, schema-contract handling and replay that does not duplicate published facts.

Principal review

Standardize 3–4 ingestion archetypes and force exceptions to justify themselves. Avoid one “golden” pattern that makes every source real time.

Your design challenge

Change one assumption—5× volume, half the latency, multi-region recovery or a 30% cost reduction. Which part of the architecture changes first, and why?

Muscle-memory practice

Principal design drills

1. Batch vs streaming

A stakeholder says, “We need real time.” What do you ask before selecting Kafka or Snowpipe Streaming?

Ask which business action changes with lower latency, required freshness in seconds/minutes, event volume/peak, ordering, replay, source guarantees, consumer behavior and acceptable operational cost. Separate consumers by SLA before choosing one estate-wide pattern.

2. Slow Snowflake query

Would you resize the warehouse first?

Usually no. Start with query profile, bytes/partitions scanned, pruning, join cardinality, spill and concurrency. Resize when evidence shows a compute/concurrency bottleneck.

3. SCD2

When should you reject SCD2?

When only current state has business value, history is available elsewhere, or the cost/semantic complexity of historization exceeds the requirement. Preserve history deliberately, not reflexively.

4. Agent architecture

When is an agent the wrong answer?

When deterministic SQL/workflow logic can solve the task, when required permissions are too broad, evaluation cannot bound risk, or the business value does not justify autonomy and operational complexity.
