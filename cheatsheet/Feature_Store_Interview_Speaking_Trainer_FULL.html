1. Walk me through one major project

BLUE = shorter interview version

One of the major projects I can talk about is the cloud migration and modernisation of our Product Feature Store at Coles. The Feature Store supports a number of AI and ML use cases, including demand forecasting, markdown and optimisation.

For these models, we need data from many Coles systems - sales, stock, pricing, promotions, range, store and calendar information. The Feature Store brings that data together, applies the required business logic and creates reusable model-ready features at a consistent grain.

Full practice speech

Sure. One of the major projects I can talk about is the cloud migration and modernisation of our Product Feature Store at Coles.

Maybe I'll first give a bit of background on what the Feature Store does, because that explains why the project was important.

One of the main use cases we support is demand forecasting. For a forecasting model, sales history alone is not enough. It needs information like promotions, pricing, stock, range, store information, holidays and other business features. The problem is that all this information doesn't come from one place. It comes from many Coles systems, and it can also come at different levels and different granularities.

So basically, the Product Feature Store brings this information together, applies the required business logic and creates reusable features at a consistent model grain. Our main grains include item-location-day and item-zone-day. We have a historical Feature Store for actual historical information and a future Feature Store for known future information such as planned promotions and holidays. These datasets are then consumed by forecasting, markdown and other optimisation use cases.

The original solution was on-prem, mainly around Oracle/BIW and legacy processing. Over time we started hitting a few limitations. A full seven-year historical rebuild could take close to two weeks. Daily processing was also taking a few hours and putting pressure on downstream ML SLAs. The code was difficult to evolve, and we didn't have a clean way to run two Feature Store versions in parallel and validate a new version before switching consumers.

So the objective was not simply to move the existing pipelines to cloud. We wanted to redesign the solution so it was scalable, easier to operate, easier to extend and safer to release.

My role covered both technical and delivery responsibilities. I was involved from requirement discussions and solution design through the detailed engineering, testing, migration and production rollout. I also worked with the data scientists, product owners, upstream data teams and other engineering teams because the Feature Store sits in the middle of quite a few dependencies.

On the architecture side, we moved the processing to Azure Databricks and used Delta on ADLS as the data layer. But the important part was the design decisions around the processing, not just the technology.

For example, one problem was maintaining separate logic for a daily run and a historical rebuild. That would create duplicate code and eventually the two paths could behave differently. So we designed the framework to use the same feature logic with a parameterised date window. For the normal daily run, it processes a rolling window to capture recent changes and late-arriving data. For a rebuild, the same logic can run for a much larger historical range. So we had one code path rather than two separate implementations.

Another problem was data volume. At item-location-day grain, if we generate every possible item, every location and every date, the dataset becomes unnecessarily large because many combinations are not valid. So we created a Feature Driving Set first. That establishes the valid active item-location-day or item-zone-day combinations, and then the feature groups are built against that set. That controls the data volume early in the pipeline.

Reliability was another design requirement. The Feature Store has many processing stages, so if a job fails late in the run, we don't want to restart everything from the beginning. We built state tracking and restartability into the framework. The framework knows what has completed successfully and can resume the appropriate processing while protecting against duplicate or inconsistent output.

We also needed a safer migration and release approach. Because the Feature Store feeds ML models, a technically successful pipeline is not enough - the feature values have to be correct. So we supported parallel versions through ModelStore metadata and used automated regression validation. That allowed the legacy and new versions to run side by side, compare the outputs, and only move consumers after we had enough confidence. It also gave us a rollback path.

One of the biggest technical challenges came during that regression testing. We initially saw thousands of mismatches between the legacy and cloud outputs. We couldn't simply say the cloud version was wrong. We had to classify the differences and find the root cause. Some were true logic differences, but some came from Oracle and Spark behaving differently - for example, the ordering of values in concatenated promotion descriptions, and some statistical mode or null-handling behaviour. We created more targeted comparison logic, including token-aware comparisons where order was not semantically important, and standardised calculations where the behaviour needed to be consistent.

There was also a scalability challenge on the future Feature Store when we extended the horizon up to 54 weeks. The item, location and promotional timeline combinations increased the memory and compute requirement. We addressed that by filtering as early as possible, using broadcast joins for appropriate static reference data, and breaking heavy processing into staged intermediate tables rather than trying to do one very large transformation.

From a delivery point of view, upstream timing was another challenge because the Feature Store depends on several source domains. If one critical source lands late, it can affect the downstream forecast SLA. So we made the dependencies visible, monitored them, and decoupled independent feature groups where possible so that everything didn't have to stop because one source was delayed.

The result was a much more scalable and operational solution. The full historical rebuild reduced from around two weeks to under 24 hours, the daily processing fitted within the required SLA, and the framework became a reusable pattern for additional Feature Stores. For me, the important part of the project was not just moving to Databricks. It was taking the limitations we had in the old solution and addressing them through specific architecture and framework decisions.

3. How to explain what your Feature Store framework does

PATTERN: CONFIGURE -> ORCHESTRATE -> EXECUTE -> TRACK STATE -> VALIDATE -> PUBLISH
Accuracy: Your project material supports the common framework, state/restartability, validation and publishing/versioning. The exact current R/AAFS -> Databricks Jobs API -> job cluster/SQL Warehouse mechanics come from your implementation knowledge. Use the wording below only where it matches your actual flow.
BLUE shorter answer

Our framework basically standardises how the Feature Stores are run. Instead of every Feature Store building its own orchestration, retry, validation and publishing logic, those common capabilities sit in the framework.

Control-M handles the enterprise schedule. Our AAFS framework in R prepares the runtime configuration and orchestrates the processing into Databricks. Depending on the workload, the processing can run on Databricks job compute, and for SQL-based workloads we can use SQL Warehouse where applicable. The actual feature outputs are stored as Delta tables.

The framework also manages runtime state, restart/catch-up behaviour, validation and publishing. So the individual feature logic can focus on the business transformation, while the framework handles the common operational lifecycle.

Full practice speech

One of the main areas I look after is the Feature Store framework. The easiest way I explain it is that it provides the common engineering and operational capabilities needed to build and run our Feature Stores.

Without a framework, every Feature Store would have to independently implement scheduling, runtime parameters, Databricks execution, retry, state management, validation and publishing. That creates a lot of duplication and makes production support harder.

So our framework separates those common capabilities from the individual feature business logic.

At the top, we have the enterprise scheduling layer. In our environment, Control-M is used to trigger the scheduled processing. Then our AAFS framework, which is in R, handles the Feature Store orchestration. It prepares the runtime information - for example which Feature Store/version is being run and the required processing window - and coordinates the execution in Databricks.

On the Databricks side, the actual feature engineering is executed using the appropriate compute. For Spark-based distributed processing, we use Databricks job compute. For SQL-based processing, SQL Warehouse can be used where that execution path applies. I normally explain these separately because the compute is not the storage. The resulting intermediate and final data is stored in Delta on the data lake.

The framework also tracks execution state. That's important because a Feature Store run has multiple steps and feature groups. If something fails, we need to know what completed successfully and what needs to be rerun. That gives us restartability and supports catch-up or backfill without blindly rerunning the whole workflow.

Another common capability is validation. Before a new output is trusted or published, we run the required data-quality and regression checks. During migration this was particularly important because we were comparing the cloud output with the legacy baseline.

Finally, once the run is successful and the quality checks are satisfied, the validated version can be published for downstream consumption. With the versioning approach, we can also keep versions separate while we validate a change before switching consumers.

So basically, when I say 'Feature Store framework', I don't mean only a set of pipelines. I mean the reusable layer that manages the lifecycle: configure the run, orchestrate it, execute the feature logic, track the state, validate the output and publish it.

4. System-design explanation - speak from top to bottom

WHY -> SOURCES -> INGEST/LAND -> DRIVING SET -> FEATURE PROCESSING -> PFS/PFuS -> DELTA -> VALIDATE/VERSION -> CONSUMERS. Across everything: orchestration, state, monitoring, governance.
BLUE shorter system-design answer

I normally start from the consumer. The Feature Store supports ML use cases such as forecasting, so we need sales, stock, pricing, promotion, range, store and calendar data from multiple source domains.

Once the source data is available in the cloud, we first establish the valid model grain through the Feature Driving Set. Then the feature groups apply the required joins, aggregations and business logic. Historical actuals go into PFS and known future information goes into PFuS. The outputs are stored in Delta.

Around that processing, the common framework handles orchestration, state/restartability, validation and publishing. Before downstream models consume a version, we validate the output and, for major changes, can run versions in parallel.

Full practice speech

If I'm explaining the system design, I normally start from why the platform exists rather than starting from Databricks.

The consumers are ML and optimisation use cases. For example, demand forecasting needs a consistent set of historical and future features. Those features depend on multiple domains - sales and margin, stock and receipts, pricing and promotions, range information, store trading information, holidays and other external or calendar signals.

Once those upstream datasets are available to the Feature Store, the first important design step is establishing the correct grain. For the main store-level use cases, that is item-location-day. We create the Feature Driving Set to identify the valid active combinations. That becomes the base against which the feature groups are calculated, rather than generating every theoretical item-location-date combination.

From there, the processing is organised into feature groups. Each group takes the required source data and applies its joins, aggregations and business rules. Where we need a different consumer grain, we aggregate or model at the appropriate level, such as item-zone-day.

We then separate historical and future feature generation because they represent different business semantics. PFS contains actual historical information such as sales, stock, waste and markdowns. PFuS contains information we know or expect for the future, such as planned promotions, price changes, holidays and range changes.

The processing runs in Databricks and the intermediate and final outputs are stored in Delta. Around that, the common AAFS framework handles orchestration, runtime configuration, state, restartability and the validation/publishing lifecycle.

Before the output is made available to consumers, we apply automated validation. During migration, this included comparison against the legacy baseline. For larger releases, versioning allows the old and new Feature Stores to coexist so data scientists can validate the new output before cutover.

So the design is not just source-to-target ETL. The important parts are controlling the grain, making feature logic reusable, separating historical and future semantics, building reliability into the framework, and putting validation and versioning before downstream ML consumption.

5. Challenge answers - full speech + blue short version

CHALLENGE PATTERN: What happened -> impact/risk -> investigate -> root cause -> options/decision -> action -> validate -> communicate -> result
Technical challenge - cloud vs legacy data parity
BLUE shorter answer

One technical challenge was data parity during the cloud migration. Our regression tests initially showed thousands of mismatches between the legacy and Databricks outputs. Because this data feeds ML models, we couldn't ignore them.

We broke the mismatches into categories and traced sample item-location-day records through the logic. Some were real issues, but others were semantic differences between Oracle and Spark, such as ordering of concatenated values and mode/null behaviour. We added token-aware comparisons where ordering was not meaningful and standardised the calculation logic where needed. That allowed us to separate genuine defects from harmless representation differences and build confidence in the cutover.

One of the more difficult technical challenges was proving data parity during the migration.

When we started running the cloud version in parallel with the legacy version, the automated regression tests reported thousands of mismatches. The easy response would have been to treat every mismatch as a defect, but that wasn't accurate. At the same time, we couldn't dismiss them because the Feature Store feeds ML models and a small feature difference can affect downstream behaviour.

So what we did was first classify the mismatches. We took sample keys at item, location and day level and traced the values through the legacy and cloud transformations. That helped us separate true business-logic differences from platform-specific behaviour.

For example, in some promotion-related string aggregations, Oracle and Spark returned the same set of values in a different order. Semantically the information was the same, but a direct string comparison failed. In other cases, we found differences around statistical mode calculations and null handling.

For the ordering case, we strengthened the validation so that where ordering was not meaningful, we compared the tokens semantically rather than treating a different sequence as a data defect. For calculations where behaviour needed to be consistent, we standardised the implementation.

I also made sure the communication was different for different audiences. With the engineers and data scientists, we showed sample keys, columns, calculation logic and the exact category of mismatch. With product and delivery stakeholders, we explained the impact on cutover, how much had been validated, what remained open and whether it was safe to proceed.

That approach helped us get to a much more reliable parity assessment and gave the downstream teams confidence in the cloud migration.

Design challenge - reusable framework without over-engineering
BLUE shorter answer

A key design challenge was that we were not building only one pipeline. We needed a pattern that could support multiple Feature Stores and both daily and rebuild processing. If each store built its own orchestration, retry and validation logic, we would create duplication.

So we separated common operational capabilities into the AAFS framework and kept feature-specific business logic within the Feature Store implementation. We also used one parameterised code path for daily and rebuild processing. The trade-off was more upfront framework design, but it gave us consistency, restartability and reuse.

One design challenge was deciding how much should sit in a common framework and how much should stay specific to each Feature Store.

We knew we were not building only one data pipeline. We had multiple Feature Stores and different feature groups, but many operational requirements were the same - orchestration, runtime configuration, state, retry, validation and publishing.

If we built all of that separately for every Feature Store, the first implementation might be faster, but over time we would have duplicated logic, inconsistent support patterns and more effort every time we introduced a new store.

So the design decision was to separate common platform behaviour from feature-specific business logic. The AAFS framework handled the common execution lifecycle, while the Feature Store implementations focused on the actual data transformations and business rules.

We applied the same thinking to daily versus historical processing. Instead of separate codebases, we used the same feature logic and changed the processing window through parameters. That reduces the risk of the daily path and rebuild path drifting apart.

The trade-off is that a reusable framework needs more upfront thought and stronger standards. You also have to avoid making it so generic that it becomes difficult to understand. So the framework should standardise genuinely common behaviour, but not hide every piece of business logic behind abstraction.

That balance gave us a reusable pattern that could support subsequent Feature Stores without turning every new use case into a completely new engineering solution.

Delivery challenge - upstream delay and downstream SLA
BLUE shorter answer

One delivery challenge was upstream dependency timing. The Feature Store depends on several source domains, so if a critical feed lands late, the downstream forecasting SLA can be affected.

We made the critical dependencies visible, monitored their status and separated independent feature groups where possible so one delayed source didn't unnecessarily block everything. From a delivery side, I communicated the business impact, expected delay, mitigation and decision point rather than only reporting a technical failure.

One delivery challenge was managing upstream dependencies while still protecting the downstream SLA.

The Feature Store consumes data from several domains. Sometimes the Feature Store itself is healthy, but an upstream feed lands late. If we simply wait without understanding the dependency, we can lose a large part of the processing window and then the forecasting or other downstream teams are affected.

So the first thing was to identify which dependencies were actually critical for a particular feature group and which processing could continue independently. We made the dependency status visible and monitored it rather than discovering the problem only after the Feature Store had already missed its start time.

Where the architecture allowed it, independent feature groups were decoupled so they could continue instead of blocking the entire workflow.

From a delivery perspective, communication was just as important. I wouldn't tell a product owner only that an upstream job failed. I would explain which Feature Store output is affected, what downstream capability is at risk, what we are doing to mitigate it, the expected recovery time and whether we need a release or business decision.

That helped us manage the issue as an end-to-end delivery risk rather than treating it as somebody else's upstream technical problem.

Performance/scalability challenge - PFuS 54-week horizon
BLUE shorter answer

When the future horizon expanded towards 54 weeks, the item-location-promotion combinations increased significantly and we saw memory and compute pressure. We changed the processing so filters were applied earlier, used broadcast joins for appropriate small/static references, and split heavy transformations into staged intermediate processing. The principle was to reduce data before expensive joins and avoid one oversized execution plan.

A good scalability example is the future Feature Store. When the future horizon was extended up to 54 weeks, the amount of data involved in combining items, locations and future promotional timelines increased significantly.

The issue wasn't something we wanted to solve just by increasing cluster size. First we looked at where the data volume was being created and where the expensive joins were happening.

We pushed filters as early as possible so unnecessary records didn't travel through the rest of the plan. For small or static reference datasets, we used broadcast joins where appropriate to avoid unnecessary shuffle. And for some of the heavier aggregations, we separated the processing into staged intermediate checkpoints rather than building one very large transformation.

The design principle was simple: reduce the dataset early, choose the join strategy based on the data, and break very heavy work into manageable stages. That helped control memory and compute cost as the future horizon increased.

6. How I communicate and work with business

BUSINESS COMMUNICATION: Understand outcome -> translate to data requirement -> play back design -> make assumptions visible -> give status/risk in business impact -> confirm decision
BLUE shorter answer

I work with the business mainly from discovery through delivery. I first try to understand the outcome they need rather than jumping into the data solution - for example, what the model or application is trying to do, what level of data it needs, how much history or future horizon is required, and which business rules are important.

Then I translate that into the data and architecture requirements and play the solution back in simple terms. During delivery, I communicate milestones, dependencies and risks in terms of impact. If there is a technical issue, I don't start with Spark or a failed job; I explain what is affected, the mitigation, expected timeline and any decision needed from them.

Full practice speech

I engage with the business quite a lot, particularly during discovery and when we are introducing a new capability or making a major change.

I normally don't start by asking them technical questions. I first try to understand what they are trying to achieve. For example, if the use case is forecasting, I want to understand what is being forecast, at what level, how far into the future, how frequently it needs to be refreshed and what business events can change the result.

From there, I translate that into data requirements. That might mean we need a particular item-location-day grain, a certain amount of historical data, future promotion information, range state or another business rule.

Once we have a proposed design, I play it back in a way that makes sense to that audience. With a product owner or business stakeholder, I focus on what data or capability they will get, when it will be available, the assumptions and dependencies, and any trade-offs they need to understand. I don't take them through cluster configuration or Spark implementation unless it is relevant to their decision.

During delivery, I keep the communication around progress, dependencies, risk and decisions. If something goes wrong, I try not to send a message like 'the Databricks job failed'. I would say what output is affected, what that means for the forecast or release, what we know about the cause, what mitigation we have, and when we expect the next update.

With data scientists and engineers, I go much deeper because they need the technical evidence - sample records, feature definitions, schema changes, regression results and root cause.

So my communication changes based on the audience, but I try to keep the same principle: make the problem and impact clear, give evidence, explain the options or action, and make sure everyone understands the next step.
