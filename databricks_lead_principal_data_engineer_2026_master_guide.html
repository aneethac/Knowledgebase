Lakeflow Connect

CURRENT PLATFORM
Managed ingestion for enterprise apps, databases, cloud storage and message buses. Principal rule: start with the most managed layer that meets requirements; custom-build only for a concrete gap.
“I treat connector ownership as a lifecycle cost. If Lakeflow Connect supports the source, CDC semantics, latency and schema behavior I need, I prefer it to maintaining custom extractors. Custom code is justified by unsupported semantics, transformations at ingress, latency or networking constraints.”

API ingestion pattern

REST API → Auth → Pagination → Rate limit/backoff → Cursor/checkpoint → Raw JSON/Delta → Normalize → DQ → Curated Persist: request/batch id • cursor • response status • extracted rows source timestamp • ingestion timestamp • retry count
Never make the LLM or notebook state your checkpoint. Operational extraction state must be durable and deterministic.
3. Delta Lake — Production Knowledge

Delta capabilities you must be able to explain

ACID + transaction logReliable concurrent table operations and atomic commits over object storage.
MERGEUpsert/delete/change application; SCD and CDC building block.
Schema enforcement/evolutionControl expected schema and additive/type evolution deliberately.
Time TravelQuery historical table versions/timestamps within retention.
Change Data FeedExpose row-level changes between table versions for downstream incremental processing.
Deletion vectorsRepresent row changes without immediately rewriting whole data files; improve mutation performance.
Liquid clusteringFlexible/adaptive data layout; preferred over rigid partition/Z-order thinking for many new tables.
Predictive optimizationManaged maintenance based on UC-observed access patterns.
CloneUseful for dev/test and controlled data copies; know shallow/deep concepts where applicable.

MERGE / SCD1

SQL
MERGE INTO silver.customer t
USING staged_customer s
ON t.customer_id = s.customer_id
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

AUTO CDC / SCD

2026
Lakeflow pipelines can declaratively apply CDC and materialize SCD Type 1 or Type 2. Current 2026 releases also add areas such as bitemporal tracking and liquid clustering support on AUTO CDC targets.
“For source CDC I preserve sequencing and delete semantics in bronze, then use AUTO CDC when its declarative semantics match the requirement. I use custom MERGE only when business-specific conflict, temporal or replay behavior exceeds the managed pattern.”

Partitioning vs liquid clustering

“I no longer default to physical date partitioning just because the table is large. I consider access patterns, cardinality, data growth and platform-managed optimization. Liquid clustering reduces the rigidity and maintenance burden of static partition/Z-order strategies and can evolve with query patterns.”
4. Spark Internals & Performance — Interview Depth

Spark execution mental model

MEMORISE
Action ↓ Logical Plan ↓ Catalyst Optimizer Physical Plan ↓ Job ↓ Stages separated by shuffle boundaries ↓ Tasks ≈ partitions ↓ Executors execute tasks
Lead interviews expect you to connect a slow workload to shuffle, partition count, skew, joins, spill, serialization and file layout—not simply say “increase cluster size.”

Performance diagnosis matrix

SymptomLikely causeActions
Huge shuffleWide join/group/windowFilter/project early, improve join strategy, repartition only intentionally.
One/few tasks very slowData skewAQE/skew join, salt extreme keys, pre-aggregate, isolate hot keys.
Disk spillWorking set > execution memoryReduce shuffle/data, improve partitions/join, then consider larger compute.
Too many tiny tasks/filesOverpartitioning/small filesManaged optimization, compaction, fewer output partitions.
OOM drivercollect/toPandas/large metadataKeep distributed, limit collection, reduce driver-side state.
Broadcast failure“Small” side not actually smallCheck statistics/size; avoid forced broadcast blindly.
Slow Python UDFPython serialization boundaryPrefer built-in Spark SQL functions; vectorized/Pandas UDF only if necessary.

Join selection

Broadcast hash joinSmall side can be replicated; removes large shuffle.
Sort merge joinCommon large-large equi-join; shuffle + sort.
Shuffle hashCan be chosen for suitable partitioned inputs.
AQERuntime plan adaptation: coalesce partitions, skew handling, join strategy changes.

Repartition vs coalesce

“I use repartition when I intentionally need a new distribution, accepting a shuffle. I use coalesce mainly to reduce partitions without a full redistribution when that is safe. I avoid using either as a ritual; partition count should follow data volume and downstream work.”

Photon + serverless

Know when Databricks-native optimized execution/serverless reduces operational tuning, but still understand Spark/data-layout fundamentals because poor joins, skew and excessive scans remain architecture problems.
5. Structured Streaming

Streaming concepts

Micro-batchDefault Structured Streaming execution model for many workloads.
CheckpointProgress/state for restart/recovery. Treat as pipeline state.
Event timeWhen event occurred at source.
Processing timeWhen platform processes it.
WatermarkBound state and define tolerated lateness for stateful operations.
Stateful operationsAggregations, dedupe, stream-stream joins; require state management.
Trigger AvailableNowIncremental batch: process all currently available data then stop.
foreachBatchCustom logic per micro-batch; use carefully for idempotency.

Streaming design answer

“I start with the freshness SLA. Streaming adds state, checkpoint, late-data and operational complexity, so I do not choose it for a five-minute business requirement if incremental batch satisfies the SLA. When streaming is justified, I define event-time semantics, allowed lateness, deduplication key, replay boundary and state growth before implementation.”

“I prefer declarative pipelines for common production patterns because they reduce orchestration, quality and state-management code. I drop to Structured Streaming when I need an API or stateful behavior the declarative layer cannot express. Managed-first is an operating-model decision, not a loss of engineering rigor.”

8. Unity Catalog, Security & Governance

Unity Catalog mental model

CORE
Metastore ↓ Catalog ↓ Schema ↓ Tables / Views / Volumes / Functions / Models / Connections ... Governance: RBAC • ownership • lineage • row filters • column masks tags/classification • audit • sharing • external locations/credentials

Managed vs external tables

“For data whose lifecycle Databricks owns, I prefer UC managed tables because platform-managed storage and predictive optimization reduce operational burden. I choose external tables when external ownership/interoperability/lifecycle requirements justify it.”

Federation vs ingest

“Federation is useful when I need governed access without copying data, especially for exploration or lower-volume queries. For high-throughput repeated analytics, SLAs, historical replay or source isolation, I usually ingest/materialize because federation retains dependency on the operational source.”

Delta Sharing / Open Sharing

Know provider/recipient concepts, governed sharing without building copy pipelines, and why sharing is preferable to proliferating extracts for many cross-organization use cases.
9. Iceberg & Open Lakehouse

Delta vs Iceberg decision

“I treat open table format as an interoperability decision. If Databricks owns the lifecycle and most workloads execute on Databricks, Delta managed tables are the simplest path. If multiple engines need a shared open table asset or an Iceberg estate already exists, managed/external Iceberg capabilities become relevant. I do not choose a format because it is fashionable.”

12. Reference System Designs

A. Batch / incremental lakehouse

DB/SaaS/Files → Lakeflow Connect / landing → Bronze Delta → Silver DQ + dedupe + CDC → Gold facts/dims → SQL/BI/ML → Lakeflow Jobs → SLA/DQ/cost monitoring

B. Event streaming

Kafka/Event Bus → Lakeflow/Structured Streaming → Bronze events + checkpoint → watermark/dedupe/stateful transforms → Silver streaming tables → real-time Gold aggregates → consumers Monitor: input rate • processing rate • lag • state size late records • duplicates • checkpoint failures • freshness

C. Database CDC

Operational DB → WAL/CDC → Lakeflow Connect/CDC tool → Bronze change log (I/U/D + sequence + source time) → AUTO CDC / MERGE → Current state + SCD history → reconciliation + lag + delete monitoring

D. API ingestion

REST API → extractor → durable cursor/checkpoint → Raw JSON Delta → normalization → Silver → Gold Retries + backoff + rate limits + dead-letter/quarantine → API health + row-count + freshness metrics

E. Federation-first discovery → materialized production

External DB → Lakehouse Federation → profile/prototype ↓ when workload justifies Managed ingestion → Delta → production transformations
Useful Principal pattern: avoid copying first, but materialize once source load, repeated scans, history, SLA or isolation justify it.

14. CI/CD, Git & Platform Engineering

Declarative Automation Bundles lifecycle

RENAMED
Git branch → code + YAML resources → databricks bundle validate → CI tests/lint → deploy DEV target → integration tests → PR approval → deploy TEST/PROD target → run job/pipeline → monitor deployment + workload
Bundles are the deployment packaging/IaC mechanism; they do not replace Git, your CI engine, Terraform for all infrastructure, or runtime orchestration semantics.

Terraform vs Bundles

“I use Terraform for account/workspace/platform infrastructure and long-lived governance objects where appropriate; Bundles for application/workload resources and code deployment. The exact boundary depends on team ownership, but I avoid two tools owning the same resource.”

Production identities

Use service principals/workload identity rather than personal credentials. Separate deploy identity from runtime identity when useful. Apply least privilege through UC and workspace/resource permissions.

Incident flow

Alert → assess business impact → contain bad publication → classify source/schema/data/code/compute/security issue → diagnose from evidence → retry/replay/backfill → reconcile → restore downstream freshness → communicate → RCA → prevention
“A green rerun is not recovery. Recovery is complete after data reconciliation, downstream freshness confirmation and consumer impact closure.”

Backfill & idempotency

“I design the normal pipeline so historical ranges can be replayed using the same transformation semantics. Stable keys, deterministic transforms and MERGE/replace-range semantics make retries idempotent. A separate emergency-only backfill code path is a smell.”

17. Lead vs Principal Interview Delivery

Same problem, different level

Lead/Senior

“I would use Auto Loader into Bronze, validate schema and duplicates, MERGE changes into Silver, build Gold marts, orchestrate with Lakeflow Jobs and monitor freshness, DQ and failures.”

Principal

“I first validate the required freshness and source change semantics. I choose the highest managed ingestion layer that satisfies them, preserve replayable source state, define contracts and ownership at domain boundaries, and design idempotency/recovery before scheduling. I isolate compute and cost by workload, enforce governance through UC, and define measurable SLOs and operational ownership before production.”

Principal answer framework

PRACTISE
1. Clarify business outcome + SLA 2. Quantify volume/growth/concurrency 3. Understand source/change semantics 4. State architecture and why 5. Explain alternatives rejected 6. Explain correctness/replay/idempotency 7. Explain security/governance 8. Explain performance/cost 9. Explain monitoring/operations 10. Explain evolution/scale/failure trade-offs
