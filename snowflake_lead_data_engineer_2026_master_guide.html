COPY INTO — batch load

SQL TO KNOW
Core pattern
CREATE FILE FORMAT ff_parquet TYPE = PARQUET;

CREATE STAGE ext_stage
  URL='azure://...'
  STORAGE_INTEGRATION=my_storage_int
  FILE_FORMAT=ff_parquet;

COPY INTO raw.orders
FROM @ext_stage/orders/
FILE_FORMAT=(FORMAT_NAME=ff_parquet)
MATCH_BY_COLUMN_NAME=CASE_INSENSITIVE;
Bulk-load design: size files for parallelism rather than producing thousands of tiny files. Snowflake documentation recommends roughly 100–250 MB compressed or larger as a useful target.

Snowpipe — continuous FILE ingestion

KNOW VS STREAMING
Concept + syntax
CREATE PIPE orders_pipe
  AUTO_INGEST = TRUE
AS
COPY INTO raw.orders
FROM @orders_stage
FILE_FORMAT=(FORMAT_NAME=ff_json);
Mental model: cloud file arrives → notification → Snowpipe sees it → serverless COPY logic loads it.
Common interview trap: Snowpipe ≠ Snowpipe Streaming. Snowpipe loads files; Snowpipe Streaming ingests rows.

Snowpipe Streaming — current low-latency ingestion

2026 IMPORTANT
High-performance architecture supports Java, Python, Node.js SDKs, REST, Kafka, CDC and Iceberg targets.
Use for application events, Kafka, IoT and CDC where the natural unit is a row/event and seconds-level freshness matters.
Human interview answer: “If the producer already emits files, I keep it simple with Snowpipe. If it emits events or CDC rows and I need seconds-level freshness, I use Snowpipe Streaming. I don’t create artificial files just to feed Snowpipe.”

Openflow — where it fits

NEWER AREAPRINCIPAL
Snowflake’s connector/integration layer for third-party sources. Current documented connectors include Kafka, Kinesis, MongoDB, Jira Cloud, Salesforce Bulk API, SharePoint, Dataverse and others.
Principal framing: “I first ask whether ingestion is a commodity connector problem or custom engineering problem. If a supported managed connector meets CDC, latency, security and recovery requirements, I prefer that over owning bespoke code. I reserve custom SDK/API ingestion for source-specific semantics or latency/processing needs.”
3. Transformations, CDC, SCD and Load Modes

Full vs append vs incremental vs CDC — selection guide

ModeUse whenProsRisks / trade-off
Full reloadSmall dimension/reference table; source lacks change tracking; occasional rebuildSimple and deterministicExpensive at scale; longer SLA; unnecessary rewrite
Append-onlyImmutable events/logs/transactionsFast, simple, replayableDuplicates/late events need handling
Incremental high-watermarkReliable updated_at / monotonically increasing keyLower compute than fullLate/out-of-order updates can be missed without overlap
CDCNeed inserts + updates + deletes from operational sourceEfficient and semantically completeMore state, ordering and recovery complexity
Snapshot/SCD2Need history of attribute changesAudit/historyStorage growth and effective-date logic

MERGE — upsert / SCD1 workhorse

MEMORISE
Pattern
MERGE INTO core.customer t
USING stg_customer s
  ON t.customer_id = s.customer_id
WHEN MATCHED THEN UPDATE SET
  t.name = s.name,
  t.updated_at = s.updated_at
WHEN NOT MATCHED THEN INSERT
  (customer_id, name, updated_at)
VALUES
  (s.customer_id, s.name, s.updated_at);
SCD1 means overwrite current attributes; no history retained.

SCD2 — history model

INTERVIEW
Typical columns: business_key, attributes, valid_from, valid_to, is_current, hash/version.
Conceptual SQL steps
-- 1. Detect changed current records
-- 2. Expire old current row
UPDATE dim_customer d
SET valid_to = CURRENT_TIMESTAMP(),
    is_current = FALSE
FROM stg_customer s
WHERE d.customer_id = s.customer_id
  AND d.is_current = TRUE
  AND d.attr_hash <> s.attr_hash;

-- 3. Insert new version for new/changed keys
INSERT INTO dim_customer (...)
SELECT ..., CURRENT_TIMESTAMP(), NULL, TRUE
FROM stg_customer s
...
Human answer: “For SCD2 I separate change detection from versioning semantics. I need a stable business key, a deterministic way to identify attribute changes, and effective dates/current flag. I also define how late-arriving source updates affect historical validity.”

Streams + Tasks

NATIVE CDC
Pattern
CREATE STREAM orders_stream
ON TABLE raw.orders;

CREATE TASK merge_orders
  WAREHOUSE = etl_wh
  SCHEDULE = '5 MINUTE'
WHEN SYSTEM$STREAM_HAS_DATA('orders_stream')
AS
MERGE INTO core.orders t
USING orders_stream s
ON t.order_id = s.order_id
...
Use when you want explicit CDC consumption and procedural/orchestrated logic. A stream is not a duplicate table; think change metadata/offset over the source.

Dynamic Tables

VERY IMPORTANT 2026
Declarative pipeline
CREATE DYNAMIC TABLE refined.orders_clean
  TARGET_LAG = '5 minutes'
  WAREHOUSE = dt_wh
  REFRESH_MODE = AUTO
AS
SELECT ...
FROM raw.orders
WHERE ...;
Snowflake maintains the SELECT result and dependency graph. Current refresh modes include AUTO, INCREMENTAL, FULL, ADAPTIVE and advanced custom incremental capabilities where applicable.
Streams/Tasks vs Dynamic Tables: “If the transformation can be expressed declaratively as SELECTs and freshness is the main requirement, I prefer Dynamic Tables. If I need procedural branching, custom DML, stored procedures, precise workflow control or sub-minute semantics, Streams/Tasks or an external orchestrator may be better.”

Dynamic Table vs Stream/Task vs dbt — architecture decision

PRINCIPAL
NeedPrefer
Snowflake-native declarative near-real-time SQL pipelineDynamic Tables
Explicit CDC, MERGE, procedure calls or conditional task graphStreams + Tasks
Cross-platform transformation engineering, Git-first modular SQL, tests/docs/CI and team workflowdbt

Principal delivery: “I don’t select orchestration because one tool is fashionable. I separate data movement, transformation semantics and workflow orchestration, then choose the least complex control plane that satisfies SLA, observability, recovery and team-operability requirements.”
4. Performance & Cost Optimization

Micro-partitions & pruning

CORE CONCEPTCERT
Snowflake automatically organizes table data into immutable columnar micro-partitions and keeps metadata such as value ranges. The optimizer can skip irrelevant partitions.
Your first performance question should often be: “How much data is being scanned, and is pruning effective?”—not “Should I immediately increase warehouse size?”

Warehouse sizing — simple rule

SymptomAction
Single query spills to local/remote storage, CPU/memory boundConsider scaling UP after SQL/pruning review
Queries are individually fine but queue under concurrencyScale OUT / multi-cluster or isolate workloads
ETL warehouse idle most of dayAuto-suspend quickly; auto-resume
BI cache repeatedly lost because warehouse suspendsBalance suspension cost against warm warehouse cache
Mixed ETL + BI contentionSeparate warehouses by workload/SLA
Interview answer: “I size from observed workload, not table size alone. Scale-up improves resources available to a query; scale-out addresses concurrency. I inspect Query Profile, scan/pruning, spill and queue time before spending more credits.”

Performance toolbox

Clustering key / Automatic ClusteringLarge tables with recurring range/filter patterns and poor natural clustering.
Search Optimization ServiceHighly selective point lookups, substring/semi-structured/geospatial patterns where supported.
Query Acceleration ServiceEligible heavy queries; offloads portions to serverless compute.
Materialized ViewRepeated expensive query shape where automatic maintenance is worthwhile.
Warehouse cacheRepeated access while warehouse remains running.
Result cacheExact reusable results when underlying data/query conditions permit.
Query Profile / QUERY_HISTORYDiagnose scan, joins, queue, spill, skew-like symptoms and cost.

Performance diagnosis order — Principal-level

USE THIS IN INTERVIEW
1. Is the SQL logically efficient? ↓ 2. Is predicate / column pruning good? ↓ 3. Is data layout/clustering appropriate? ↓ 4. Are joins causing explosion? ↓ 5. Is there memory spill? ↓ 6. Is the issue single-query capacity or concurrency? ↓ 7. Would SOS / QAS / MV materially help? ↓ 8. Only then increase recurring spend.
Principal phrasing: “I optimize for cost per useful workload, not just query latency. A 20-second query on a small warehouse can be economically better than a 5-second query on an oversized warehouse if the SLA allows it.”
5. Iceberg, Lakehouse & Medallion

Can Snowflake use Medallion architecture?

YES
Sources ↓ RAW / BRONZE immutable landed events/files/CDC ↓ REFINED / SILVER cleaned, typed, deduplicated, conformed ↓ CURATED / GOLD dimensional models, marts, aggregates, features ↓ BI / ML / Apps / Sharing
Medallion is a logical data-engineering layering pattern. In Snowflake it is commonly expressed with schemas/databases and tables/views/dynamic tables/dbt models.

Why Iceberg in Snowflake?

COF-C03 RELEVANT
Iceberg is an open table format with ACID transactions, schema evolution, hidden partitioning and snapshots. Snowflake can query/manage Iceberg tables while data resides in open Parquet files.
Choose Iceberg when: data must stay in lake/object storage, multiple engines need access, open-format portability matters, or an existing lake must be reused.
Do not choose it automatically. Native Snowflake tables are often simpler when all important consumers live in Snowflake and portability is not required.

Native table vs Iceberg

Human response: “I treat Iceberg as an interoperability decision, not a performance fashion. If Snowflake is the primary compute and governance plane and there is no external-engine requirement, native tables reduce operational surface area. If Spark, Snowflake and other engines must share an open data asset, Iceberg becomes strategically useful.”
6. Snowpark, APIs, Apps and Extensibility

Snowpark

Developer APIs for processing data in Snowflake with languages such as Python. Useful when logic is easier to express programmatically than in pure SQL while keeping computation close to data.
Databricks bridge: “I would not port Spark code line-for-line. I first decide whether the transformation should be SQL. I use Snowpark where Python/dataframe logic, reusable libraries or procedural code materially improves maintainability.”

UDF vs Stored Procedure vs Snowpark

UDFReusable function in a SQL expression; row/value-oriented logic.
Stored ProcedureProcedural workflow/DML/control logic executed in Snowflake.
Snowpark DataFrameProgrammatic transformation pipelines while leveraging Snowflake execution.

Apps / external integration

Know the landscape: connectors/drivers, REST APIs, external access integrations, Streamlit in Snowflake, Native Apps, Snowpark Container Services, Cortex services. A Lead DE does not need expert app-development depth, but should know where the data platform boundary is.

9. dbt Deep Dive — Why it exists and how it fits Snowflake

What dbt actually is

MENTAL MODEL
dbt does transformation engineering, not general-purpose ingestion. You define SQL/Python models, dependencies, tests, metadata and deployment workflow; dbt compiles and executes them on the data platform.
Source data already in Snowflake ↓ dbt source() ↓ staging models ↓ ref() intermediate models ↓ marts / facts / dimensions ↓ tests + docs + lineage + CI/CD
Why not just SQL scripts? dbt adds modularity, dependency graph, environments, reusable macros, tests, documentation, lineage and software-engineering workflow around SQL transformation.

source() vs ref()

MEMORISE
Pattern
-- raw table managed outside dbt
select *
from {{ source('raw', 'orders') }}

-- upstream dbt model
select *
from {{ ref('stg_orders') }}
source() references externally loaded source assets. ref() creates model dependencies and lets dbt build the DAG.

dbt incremental MERGE

INTERVIEW

{{ config(
    materialized='incremental',
    unique_key='event_id',
    incremental_strategy='merge'

select *
from {{ source('raw','events') }}

{% if is_incremental() %}
where event_ts >= (

The overlap window protects against late arrivals. Make the transformation idempotent via stable unique keys.

dbt snapshots = SCD2-like history

Snapshots record how mutable source rows change over time. Use a timestamp strategy when a reliable updated_at exists; check strategy when you need to compare selected columns.
Human answer: “I use snapshots for source-state history, while an explicit dimensional SCD2 model may be better when I need business-specific effective dating and dimensional semantics.”

dbt + Snowflake architecture choices

PRINCIPAL
QuestionPrincipal answer
dbt vs Dynamic Tables?dbt gives engineering workflow and cross-platform DAG/tests/docs; Dynamic Tables give Snowflake-native declarative refresh. They can coexist. Choose ownership boundaries deliberately.

12. Interview Questions — Human, Speakable Answers

Practice answers

How do you choose batch vs streaming?

“I use the business freshness SLA first. If minutes or hours are acceptable, batch is cheaper and operationally simpler. If an operational use case genuinely needs seconds-level freshness, I use streaming. I also check whether the source naturally produces files or events because forcing an unnatural ingestion format creates complexity.”

How do you decide full vs incremental?

“I compare table size, change ratio, rebuild duration, source change semantics and recovery complexity. Full is fine for small tables. For large facts I prefer append or incremental. For mutable operational entities I use CDC or MERGE. I don’t introduce incremental state unless it buys meaningful SLA or cost improvement.”

How do you optimize a slow Snowflake query?

“I start with Query Profile: bytes/partitions scanned, pruning, joins, spill and queue time. Then I determine whether the bottleneck is SQL/data layout, single-query compute, or concurrency. Only after that do I consider clustering, SOS/QAS or resizing compute.”

How do you choose warehouse size?

“I benchmark representative workloads. I scale up when a query needs more compute/memory and scale out when concurrency is the issue. I isolate workloads by SLA and cost center, use auto-suspend/resume, and track credits per workload rather than choosing one oversized warehouse for everything.”

Why dbt with Snowflake?

“Snowflake executes SQL; dbt provides the transformation engineering layer around it—modular models, DAG dependencies, testing, documentation, environments and CI/CD. I use dbt when team maintainability and governed transformation lifecycle matter, not because Snowflake lacks SQL.”

Would you use medallion in Snowflake?

“Yes. Bronze/silver/gold is a logical layering pattern. I might call them raw/refined/curated, but the principle is the same: preserve ingest fidelity, isolate cleansing/conformance, then expose stable consumer models.”

16. Reference System Design Flows

System Design A — Daily / hourly batch

Source DB / SaaS / Files ↓ Extract / Export ↓ Object Storage (S3 / ADLS / GCS) ↓ COPY INTO Snowflake RAW ↓ Validation + Audit Counts ↓ dbt / Dynamic Tables / Tasks ↓ REFINED ↓ SCD / Facts / Dimensions ↓ CURATED / MART ↓ BI / ML / Sharing ↓ Freshness + DQ + Cost Monitoring
Choose when: minutes-to-hours freshness is sufficient. This is generally simpler, easier to recover, and cheaper to operate than streaming.

System Design B — Near-real-time file ingestion

Application / Source ↓ produces files Cloud Object Storage ↓ notifications Snowpipe ↓ RAW Snowflake Tables ↓ Dynamic Tables OR Streams + Tasks ↓ REFINED ↓ Serving / BI ↓ Pipe + freshness + DQ monitoring
Choose when: source naturally produces files and low-minute freshness is enough.

System Design C — Event streaming

App / Kafka / Event Bus ↓ Snowpipe Streaming / Connector ↓ RAW EVENTS ↓ Dedup + event-time handling ↓ Dynamic Tables / Streams+Tasks / dbt microbatch ↓ Near-real-time aggregates ↓ Operational analytics / downstream consumers Monitoring: ingestion latency • duplicate rate • event lag • reject rate • freshness
Principal answer: “Streaming is not simply ‘batch but faster’. I explicitly design event time vs processing time, ordering expectations, late events, replay boundaries, dedup keys, state and consumer freshness.”

System Design D — Database CDC / WAL

VERY COMMON INTERVIEW
Postgres / MySQL / SQL Server / Oracle ↓ Transaction Log / WAL / CDC Feed ↓ CDC Connector / Openflow / Partner Tool ↓ RAW CDC TABLE business_key operation (I/U/D) source_lsn / offset source_timestamp ingestion_timestamp ↓ Ordering + Deduplication ↓ MERGE / SCD handling ↓ CURRENT STATE + HISTORY ↓ Reconciliation / lag / offset monitoring
Speakable answer: “For a large mutable operational table, I prefer log-based CDC over repeated full extracts because it captures inserts, updates and deletes with less source impact. I preserve source offset or LSN and operation metadata in raw so I can replay deterministically. Then I apply ordered changes into current-state or SCD models.”

System Design E — API ingestion

REST / SaaS API ↓ Extraction Service / Connector ↓ Pagination Rate limiting / retries Checkpoint / cursor ↓ RAW JSON ↓ Schema normalization ↓ REFINED tables ↓ Curated models Operational state: last_success_cursor last_success_timestamp API response code metrics retry count records extracted
“For APIs I separate transport reliability from transformation. The extractor owns pagination, authentication, rate limiting, retry/backoff and checkpointing. Raw responses are preserved when practical, and downstream transformation remains idempotent.”

System Design F — Open lakehouse / Iceberg

Sources ↓ Object Storage ↓ Iceberg Tables ↙ ↘ Snowflake Spark / Databricks / Other Engines ↓ Governed semantic / curated models ↓ Consumers
“I select Iceberg when cross-engine interoperability or lake ownership is a real architectural requirement. If Snowflake is the only meaningful consumer, native tables are often operationally simpler.”
17. Data Modeling Process

Modeling flow: raw → refined → serving

RAW preserve source fidelity add ingestion metadata ↓ STAGING rename / cast / normalize / basic dedupe ↓ CONFORMED / REFINED common keys reference data reusable business rules ↓ DIMENSIONAL / DOMAIN MODEL dimensions facts SCD history ↓ MART / SEMANTIC consumer-specific metrics and aggregates
Avoid putting consumer-specific logic directly in raw ingestion. That couples transport to business semantics and makes replay/change harder.

Fact table questions

Always define grain first.
“The grain is one row per what? Order? Order line? Customer-day? Store-item-week? I define the grain before measures and joins, otherwise double-counting is almost guaranteed.”

Dimension questions

SCD1Current value only; overwrite history.
SCD2Track history with valid_from/valid_to/current.
Degenerate dimensionBusiness identifier stored in fact without separate dimension.
Conformed dimensionShared consistent dimension across marts/facts.
Late-arriving dimensionFact arrives before dimension; use unknown/inferred handling then reconcile.

SLA vs SLO vs SLI — simple explanation

SLIMeasured indicator — e.g. pipeline freshness = 12 minutes.
SLOInternal target — e.g. 99.5% of hourly loads available within 20 minutes.
SLAFormal commitment to consumers/business, possibly with consequences.
Principal engineers talk about measurable service levels, not simply “the pipeline runs every hour.”

Alerting strategy

P1Critical business data unavailable/corrupt; immediate action.
P2SLA at risk, major degradation, recoverable without immediate business outage.
P3Warning/trend such as rising cost, quality drift, delayed non-critical feed.
Do not alert on every failed SQL statement. Alert on meaningful service impact or actionable leading indicators; otherwise teams develop alert fatigue.

Operational incident flow

Alert ↓ Confirm impact / scope ↓ Stop bad downstream publication if required ↓ Identify failure class ├─ source missing ├─ schema change ├─ bad data ├─ compute/performance ├─ credentials/network └─ code/deployment ↓ Recover / retry / replay / backfill ↓ Reconcile data ↓ Resume consumers ↓ Post-incident review ↓ Prevent recurrence
Principal answer: “Recovery is not complete when the task turns green. I reconcile the recovered data, confirm downstream freshness, communicate consumer impact, and then remove the root cause or improve detection.”

20. Backfill, Replay & Recovery Design

Backfill process

Define affected date/key range ↓ Freeze or isolate overlapping production writes if needed ↓ Re-extract / identify raw source ↓ Process into temporary/backfill target ↓ Validate counts + business metrics ↓ MERGE / replace target partitions/logical range ↓ Rebuild affected downstream models ↓ Final reconciliation + consumer signoff
A good pipeline is designed so the same transformation can process both “today” and a historical date range. Backfill should not require inventing a second code path.

Idempotency

“Given the same source batch/event set, rerunning should produce the same business state. I achieve that with stable business/event keys, deterministic transformations and MERGE/overwrite semantics rather than blind append.”

Late-arriving data

“I distinguish event time from ingestion time. For batch incrementals I often use an overlap lookback and MERGE. For streaming I define allowed lateness and dedupe/reprocessing semantics. For SCD2 I decide whether late source changes revise historical validity or are applied prospectively.”

PRACTISE SPEAKING

25. Human-in-the-Loop Decision Framework

Which AI actions require approval?

RiskExamplesPolicy
LowRead metadata, summarize logs, search docs, draft SQLAutomatic
MediumRetry known-idempotent task, quarantine clearly malformed file, create draft ticketMay automate under strict predefined policy
HighProduction MERGE/backfill, warehouse/config change, modify scheduled pipelineHuman approval
CriticalDROP/TRUNCATE, privilege grants, secrets, PII export, legal deletion, broad production writeAI should not independently authorize; privileged controlled workflow

Decision formula

Can the action damage data/security? YES → approval Is the action hard to reverse? YES → approval Is the agent reasoning probabilistic? YES + consequential → approval Is outcome deterministic, bounded, idempotent and reversible? YES → candidate for automation Can policy validate before execution? NO → human review

Separate reasoning from authority

“The AI may have broad reasoning visibility but narrow execution authority. For example, it can inspect pipeline metadata across the platform but only invoke an approved `retry_pipeline(pipeline_id)` tool, rather than receiving arbitrary SQL execution rights.”

27. Responsible AI Engineering Controls

Control stack

Identity ↓ RBAC / least privilege ↓ Trusted semantic + retrieval sources ↓ Prompt / instruction controls ↓ Tool allow-list ↓ Input validation ↓ AI reasoning ↓ Output / policy validation ↓ Human approval for consequential actions ↓ Execution ↓ Immutable audit trail ↓ Observability / evaluation / feedback

Prompt injection

Any retrieved document, API response or tool output can contain malicious instructions. Treat retrieved content as untrusted data, not authority.
Use platform guardrails where available, tool allow-lists, least privilege, instruction hierarchy and approval gates. Never rely on the prompt alone as the security boundary.

AI data access

Keep Snowflake RBAC, masking and row policies as the source of truth. AI should inherit governed access—not bypass it through a highly privileged shared service account.

Agent identity

Where supported, distinguish agent-driven access from normal human/service sessions so agent actions can be governed and audited separately.

31. Interview Responses — AI + Data Engineering

Human-speakable answers to practise

How would you use agentic AI in data engineering?

“I would start with high-context, low-authority use cases—incident triage, DQ investigation, lineage impact analysis and documentation. The agent can combine structured platform metrics with RAG over runbooks and historical incidents. I only add write actions once each action is bounded, idempotent, auditable and governed by approval or policy.”

Would you let an AI agent fix production pipelines?

“Not with unrestricted authority. I separate diagnosis from execution. An agent can automatically gather evidence and recommend a fix. A deterministic, reversible action such as retrying an idempotent transient failure could eventually be automated under policy. Backfills, production DML, privilege changes and destructive operations require explicit control and usually human approval.”

When should we not use AI?

“If I can express correctness as an exact rule, I prefer deterministic engineering. Null checks, reconciliation, SCD logic, access control and financial formulas should not depend on an LLM. AI is useful where interpretation, unstructured information or multi-source contextual reasoning is the difficult part.”

How do you make an agent production-ready?

“I treat it like another production system: least-privilege identity, bounded tools, trusted semantic/retrieval context, prompt-injection protection, human approval for consequential actions, a representative evaluation suite, full traces and cost/quality monitoring. I also define fallback behavior when the model is uncertain or a tool fails.”

How does AI improve DE productivity?

“The biggest gain is reducing time spent discovering context—reading logs, tracing lineage, finding owners, searching runbooks and correlating incidents. I measure value through MTTR, investigation time, documentation coverage, review effort and successful task completion rather than counting generated SQL lines.”

What is the Principal-level difference?

“A Senior engineer can build the agent. At Principal level I define the operating model: which decisions remain deterministic, which can use probabilistic reasoning, what authority the agent receives, how access is governed, how quality is evaluated, who owns failures and how we prove business value.”
