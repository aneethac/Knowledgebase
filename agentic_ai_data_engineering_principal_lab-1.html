The one sentence to remember

An agent is an LLM placed inside a bounded decision loop, with a goal, context, tools, memory/state, observations, and stopping rules.

A chatbot mainly answers. A workflow follows predetermined steps. An agent can choose what to do next at runtime.

Principal-level rule

Start deterministic. Add agency only to the uncertain decision points.

Use normal orchestration for known ETL behavior; use an agent for diagnosis, exploration, planning, triage, or adaptive routing where rules become brittle.

Level 1

Fundamentals

LLM

Generates the next best textual/token-level continuation from context. It does not inherently know live state, execute actions, or guarantee truth.

Workflow

Developer-defined control flow. Predictable, testable, cheaper. Best for known repeatable processes.

Agent

Model-selected control flow at runtime. More adaptive but less predictable, costlier, and harder to debug.

Do not equate sophistication with maturity. L4/L5 may be less appropriate than L2/L3 for production DE because deterministic, auditable behavior is often more valuable.

When not to build an agent

Deterministic rules already solve the problem reliably.
Sub-100ms latency is mandatory.
Zero-error tolerance with no review is required.
High-volume simple processing would make model cost unjustifiable.
A standard scheduler, SQL job, validation framework or rule engine is enough.

Read vs write tools

READ

Usually idempotent and safer to parallelize. Examples: metadata, logs, table history, job status, lineage, metrics.

WRITE

Creates side effects. Examples: rerun job, alter table, publish data, open ticket, change config. Serialize, authorize, require approval when impact is non-trivial.

MCP in one sentence

Model Context Protocol (MCP) standardizes how agent hosts connect to tools and data sources. It is a connectivity/interface standard, not your enterprise authorization model and not a substitute for tool-level governance.

Principal question: “Does MCP reduce bespoke integrations here, and where do authentication, authorization, tenancy, audit and data classification still live?”

Context engineering > prompt cleverness

The best agent is often the one that sees the right evidence, not the most elaborate prompt. Control context using retrieval, summarization, isolation, metadata filters, reranking and provenance.

Never store everything. Keep stable preferences, verified facts with provenance, decisions and reusable outcomes. Expire stale facts. Do not turn model guesses into durable enterprise memory.
Advanced

Multi-agent systems

A multi-agent system makes sense when specialization, permission separation, independent context, parallelism, or clear organizational ownership genuinely require separate agents.

TopologyWhen usefulDE example
SupervisorCentral routing + mergeIncident supervisor delegates logs, lineage and DQ investigation
PipelineAssembly-line handoffRequirements → design → review
HierarchicalLarge domains / organizational delegationPlatform → domain → product agents
BlackboardShared common stateMultiple specialists update one incident state
Debate/ensembleIndependent critiqueValidate architecture or generated SQL
Failure modes: infinite ping-pong, context loss, duplicate work, diffused ownership, compounding errors. Default to one strong agent plus good tools until proven otherwise.

Example: Pipeline Operations Agent

Event: nightly sales_feature job FAILED

Agent:
1. get_job_run(run_id)
2. classify failure signature
3. get_recent_deployments(job)
4. get_upstream_freshness(inputs)
5. get_table_history(affected_tables)
6. query_dq_metrics(partitions)
7. retrieve_runbook(error_class)
8. formulate root-cause hypothesis
9. verify with one or more targeted reads
10. recommend action

IF proposed action = "rerun affected partition":
   calculate blast radius
   verify idempotency
   require approval when policy says so
   execute bounded rerun
   observe result
   log RCA + evidence + outcome
Architecture leadership

How a Principal Engineer should solution agents

Use this decision sequence

01 WHY
Define the business problem. “Reduce incident MTTR” is better than “we need an agent.” Establish baseline metrics first.
02 NEED
Prove agency is required. Separate deterministic steps from judgment-heavy steps. Prefer workflow + agentic decision points.
03 BOUND
Define autonomy boundary. Read-only? Can it write? Which writes are reversible? Where is human approval mandatory?
04 EVIDENCE
Define context sources. Authoritative metadata, logs, runbooks, lineage, metrics, schemas, deployment history. Add provenance and freshness.
05 TOOLS
Design narrow tools. Stable contracts, typed args, least privilege, idempotency keys, timeouts, retries, audit.
06 LOOP
Bound execution. Max iterations, repeated-action detection, token/cost/time budgets, confidence threshold, safe fallback.
07 EVAL
Define success before build. Golden incidents, expected diagnosis, required evidence, acceptable tool trajectory, latency/cost budget.
08 RISK
Threat-model the system. Prompt injection, exfiltration, tool poisoning, excessive agency, privilege confusion, sensitive memory.
09 RUN
Operationalize. Tracing, scorecards, rollback, kill switch, model/prompt/tool versioning, incident ownership and SLOs.
10 SCALE
Only then expand autonomy. Shadow → recommend → approval → bounded auto-remediation.

Build to learn

Enterprise projects

Project 1 — Data Platform Incident Copilot

Beginner → Intermediate Best first project.

Goal: given a failed job, gather logs + freshness + recent deploy + table history, then produce evidence-backed diagnosis and recovery recommendation.

Architecture: one agent, read-only tools, RAG over runbooks, structured RCA output, evaluation set of known incidents.

Principal extension: add approval-gated rerun with idempotency and blast-radius checks.

Project 2 — Data Quality Root-Cause Agent

Intermediate

Start from DQ variance. Agent finds affected slices, compares source/Bronze/Silver/Gold, checks freshness/deployments/schema changes, then ranks hypotheses with evidence.

Principal extension: route high-confidence low-risk issues to bounded remediation; escalate uncertain cases.

Project 3 — Enterprise Migration Assessment Agent

Advanced

Ingest package metadata or specifications; classify source, transformation complexity, dependencies, SCD behavior, code constructs and target Databricks/Snowflake patterns; generate migration + validation plan.

Principal extension: portfolio scorecard: complexity, risk, wave planning, automation suitability, review gates.

Project 4 — Data Product Discovery Agent

Advanced

Natural-language intent → catalog/lineage/RAG search → relevant datasets/features → ownership/freshness/quality → sample SQL → citations.

Principal extension: access-aware retrieval, tenant isolation, policy filters, provenance and freshness scoring.

Principal checklist before saying “agent”

Business outcome and baseline metric are defined.
We proved deterministic automation alone is insufficient.
Agency boundary and write permissions are explicit.
Authoritative context sources and freshness rules are defined.
Tools have typed contracts, least privilege and audit.
Stop conditions, budgets and retries are bounded.
Golden evaluation dataset exists before production.
HITL, rollback and kill-switch strategy exist.
Muscle memory

Principal Engineer talk track

60-second answer: “How would you design an agentic DE solution?”

“I would start with the business outcome and establish whether we really need an agent. I separate deterministic data-processing steps from decision points that genuinely benefit from model reasoning. I keep the LLM inside a bounded control plane: narrow tools, authoritative context, least-privilege access, step/time/cost limits, and explicit stopping conditions. Reads can usually be more autonomous; writes are classified by blast radius and may require approval. I define evaluation before rollout using known incidents or golden tasks, measuring not only the final answer but tool choice, arguments, latency, cost and escalation behavior. I would then roll out progressively from shadow mode to recommendations, approval-gated actions, and only finally bounded auto-remediation.”

Architecture review questions you should ask

1. What is the business outcome?
2. Why is this not a deterministic workflow?
3. Where exactly is the uncertain decision?
4. What is the source of truth for each fact?
5. Which tools are read vs write?
6. What is the blast radius of each write?
7. How do we handle stale or poisoned context?
8. What are our stop conditions?
9. What happens on model/tool failure?
10. How do we evaluate the trajectory, not just the answer?
11. What does human approval look like?
12. How do we observe, audit, version, rollback and kill the agent?
